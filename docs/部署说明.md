# 部署说明 (ansible-k8s)

本文档覆盖从**主机清单**到**Kubernetes 集群**的完整部署流程（**在线 / 离线**均支持，离线整条链路传 `-e is_offline=true`），供团队维护参考。
底座（OS 初始化 → 容器运行时 → Harbor → 负载均衡）见 [一~十一]；**Kubernetes 部署层**（etcd → 控制面 → 多 CNI → worker）见 [十二~十五]。
（项目总览见 [README.md](../README.md)；手动安装 containerd 的原始笔记见 [containerd.md](containerd.md)。）

> **准备顺序**：① 写主机清单（[一](#一主机清单inventoryhostsini-格式)）→ ② 配核心变量（[二](#二配置核心变量group_varsallenvyaml)）→ ③ 配 SSH 免密（[三](#三ssh-免密)）→ ④ 底座 + Kubernetes（[快速上手](#快速上手命令清单)）

## 快速上手（命令清单）

> 在 **cpu01（控制机）** 上执行。这里是**唯一的完整命令清单**；主机清单/变量的详细示例见 [一](#一主机清单inventoryhostsini-格式)、[二](#二配置核心变量group_varsallenvyaml)，各步细节见对应章节。
> **在线 / 离线**：默认在线；离线整条链路加 `-e is_offline=true`（或在 inventory `[all:vars]` 里设一次，见 [十六](#十六离线部署完整流程)）。

```bash
cd ansible-k8s

# 0. 生成并填 inventory + 变量(详见 一 / 二)
bash init.sh                                     # 由 tmp/hosts.example 生成 inventory/hosts(已存在则跳过不覆盖)
vim inventory/hosts                              # 主机分组 + 连接信息, 见「一」
vim inventory/group_vars/all/env.yaml            # 域名/密码/版本/CNI/is_offline, 见「二」

# ---- 底座 ----
ansible-playbook playbook/add-control-key.yaml   # (可选)控制机→各节点免密(首次无免密时加 -k)
ansible-playbook playbook/init.yaml              # 系统初始化(离线在 env.yaml 置 is_offline=true)
ansible-playbook playbook/mount-nvme.yaml        # 数据盘: hosts=[nvme_single](单盘)
ansible-playbook playbook/mount-nvme-lvm.yaml    # hosts=[nvme_lvm](多盘 2/4 块组 LVM)
#   4块3.5T交付标准改用 mount-nvme-lvm-containerfs.yaml(会清盘, 见「五」); 组留空则跳过
ansible-playbook playbook/containerd-setup.yaml  # 装 containerd(★先挂盘再装)
ansible-playbook playbook/docker-install.yaml    # 装 docker(仅 Harbor 用, 复用已装的 containerd)
ansible-playbook playbook/harbor-install.yaml    # 装 Harbor(离线镜像中转站, 必须在 k8s 之前)
ansible-playbook playbook/harbor-trust.yaml      # 各节点信任 Harbor CA 证书
docker login harbor.local.clusters -uadmin -pHarbor12345   # 验证(在装了 docker 的节点)

# ---- Kubernetes ----
ansible-playbook playbook/etcd-deploy.yaml       # 外置 etcd(建议 3/5 台奇数)
ansible-playbook playbook/k8s-install.yaml       # 首 master kubeadm init + CNI + 其余 master 加入
#   等价拆成两步(需要分步验证时用, 详见「十二」):
#     ansible-playbook playbook/k8s-init-master.yaml   # 只对第一台: kubeadm init + CNI + nodelocaldns
#     ansible-playbook playbook/k8s-add-master.yaml    # 其余 master 加入
ansible-playbook playbook/k8s-add-node.yaml      # 加 worker

# ---- 验证 ----
kubectl get nodes                                # 全部 Ready
kubectl get pod -A                               # coredns / CNI Pod Running
```

> **顺序要点**：先挂盘 → containerd → docker → harbor → etcd → k8s；docker 复用 containerd 见 [七](#七docker-与-harbor)。
> **单 / 多 master**：单 master 不设 `lbvip` 即免 LB；多 master 高可用需先配 `lbvip` + 跑 LB（[八](#八负载均衡k8s-apiserver-高可用haproxy--nginx-ha--keepalived)）。详见 [十二](#十二kubernetes-部署etcd--控制面--cni--worker)。
> **最省事验证路径**（在线单 master 最小跑通）见 [十二.1](#十二1-实机验证在线单-master-最小跑通示例)。

## 一、主机清单（inventory/hosts，INI 格式）

按角色分组，**行内**给节点设变量（`accelerator_type` / `host_ip` 等）。首次先用 `bash init.sh` 从 `tmp/hosts.example` 生成 `inventory/hosts`（已存在则跳过），再按实际填写。实际结构：

```ini
[cluster]                      # 所有节点(可带 ipmi_ip / storage_ip 等自定义变量)
node018 ansible_host=10.1.0.18

[docker]                       # 装 docker 的节点(harbor 用); accelerator_type=nvidia 装 GPU toolkit
[cri_docker_nodes]             # 用 Docker 当运行时的节点(默认走 containerd, 一般留空)

[containerd]                   # 用 containerd 的节点; accelerator_type 行内设(不指定=默认runc)
node018 accelerator_type=nvidia

[harbor]                       # Harbor 节点
10.2.0.15

[k8slb]                        # haproxy+keepalived LB 节点(用主机别名); host_ip 可省(自动按 ansible_host 探测)
10.2.0.11 host_ip=10.2.0.11
10.2.0.12 host_ip=10.2.0.12
10.2.0.13 host_ip=10.2.0.13

[etcd]                         # 外置 etcd(建议 3/5 台奇数; 单 master 可与 master 共机)
[k8s_master]                   # 控制面(单 master 放 1 台且不设 lbvip 即免 LB)
[k8s_node]                     # worker

[all:vars]                     # 全局变量: 本段只放 python 解释器 / ssh 参数
# 集群参数(chrony_ip / lbvip / vip_prefix / is_offline / kube_network_plugin 等)
# 一律在 inventory/group_vars/all/env.yaml 配置 —— group_vars 优先级高于 hosts,
# 写在 [all:vars] 会被 env.yaml 覆盖(不生效)。
# 连接身份(root 直连 / 普通用户+sudo)由 group_vars/all/connection.yaml 决定,默认 connect_as=root,
# 【不用】在这写 ansible_user / ansible_ssh_pass / ansible_become*(写了也会被 connection.yaml 覆盖);
# 首次未免密时改 connect_as=sudo 并配 bootstrap_user / bootstrap_ssh_pass / bootstrap_become_pass。
ansible_python_interpreter=/usr/bin/python3
ansible_ssh_common_args="-o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null"
```

> ⚠️ `inventory/hosts` 含密码，已被 `.gitignore` 忽略、**不提交**；仓库里 `hosts` 保留注释示例（另见 `tmp/hosts.example`）。

### 连接与免密

连接身份由 `group_vars/all/connection.yaml` 决定,**默认 `connect_as: root`**（全程 root 免密直连，本项目常态）。所以 `[all:vars]` 里【不用】再写 `ansible_user`/`ansible_ssh_pass`/`ansible_become*`。

| 情况 | 怎么配 |
|---|---|
| **已 root 免密**（常态） | 默认 `connect_as: root`，什么都不用配；`bootstrap_*` 可不填 |
| **还没配 root 免密**（首次进场只有厂商账号） | 先跑 `add-control-key.yaml -k` 下发控制机公钥即可回到 root；或临时 `env.yaml` 配 `connect_as: sudo` + `bootstrap_user` / `bootstrap_ssh_pass` / `bootstrap_become_pass` 走「普通用户 + sudo」 |
| **首次引导想自动判** | `connect_as: auto` 逐台探测（免密→root，否则 用户+sudo）——仅建议引导期临时用,见下方 ⚠ |

> ⚠️ `connect_as: auto` 的探测是「group_var 里惰性跑 ssh」，在 **`delegate_to` 委派任务**（加节点/拿 join/etcd）下委派机地址解析对不齐、易误判成「用户+sudo」而报 `bootstrap_user 未定义`；也**不认堡垒机/ProxyJump**、慢节点可能 4s 超时误判。**所以默认用 `root`,委派密集的操作别用 auto**。sudo 回退需**控制机**装 `sshpass`。

## 二、配置核心变量（group_vars/all/env.yaml）

变量分两个文件（同属 `group_vars/all`，自动合并、同优先级）：
- **`env.yaml`** —— 部署新环境「要改」的，就看这一个文件；
- **`defaults.yaml`** —— 默认（镜像清单/路径/`k8s_compat`/派生变量等），一般不动。

部署新环境**主要改这几个核心变量**（其余用默认即可）：

| 变量 | 本例值 | 说明 |
|---|---|---|
| `harbor_instances` | dns: `harbor.local.clusters`, ip: `172.171.0.206` | Harbor 域名 + 地址 |
| `containerd_version` | `1.7.32` | containerd 版本(或 `2.2.3`) |
| `runc_version` | `1.1.12` | runc 版本 |
| `container_base` | `/var/lib/container` | 数据盘主挂载点（详见 [五](#五数据盘挂载)） |
| `data_root` | `/var/lib/docker` | docker 数据目录 |
| `harbor_copy_path` | `/data/harbor-install` | harbor 安装目录 |
| `data_volume` | `/data/harbor-data` | harbor 数据目录 |
| `harbor_admin_username` / `harbor_admin_password` | `admin` / `Harbor12345` | harbor 管理员(建议改密码) |

> 其它变量（镜像清单、docker_softs、nginx 路径、加速器映射等）一般用默认。完整清单见 [十](#十关键变量参考group_varsallenvyaml)。

### 四个必填项（`defaults.yaml` 故意不兜底）

⚠ 这四项与其它变量不同：**没有兜底默认值，缺了会明确报错**。

| 变量 | 参考值 | 为什么必填 |
|---|---|---|
| `pod_subnet` | `10.244.0.0/12` | 进 kubeadm `podSubnet`，**建完集群不可改**（要改等于重建） |
| `service_subnet` | `10.96.0.0/12` | 进 kubeadm `serviceSubnet`，同上 |
| `dns_domain` | `cluster.local` | 进 apiserver 证书 SAN 与 kubelet `clusterDomain`，改了得重签证书 |
| `etcd_data_dir` | `/var/lib/etcd` | etcd 数据落盘位置，指向别处等于指向空目录、集群起不来；`etcd-destroy` 还按它删目录 |

这四项**其余变量都有的 `defaults.yaml` 兜底，它们没有**——因为猜错的代价是重建集群或重签证书，"明确报错"比"静默取默认值"安全。缺任一项时，下列 role 的预检 assert 会拦住并点名缺哪几个：

| 变量 | 拦在哪 |
|---|---|
| `pod_subnet` / `service_subnet` / `dns_domain` | `kube-init-master`（`k8s-install` / `k8s-init-master` 必经） |
| `pod_subnet` | `cni`（单独跑 `k8s-cni.yaml` / `k8s-cni-switch.yaml` 时也拦） |
| `dns_domain` | `nodelocaldns` |
| `etcd_data_dir` | `etcd-common`（`etcd-deploy` / `etcd-install` / `etcd-scale-up` 必经）、`etcd-destroy` |

**已有集群查实际值**（别照抄参考值）：

```bash
kubectl -n kube-system get cm kubeadm-config -o yaml | grep -E 'Subnet|dnsDomain'
grep data-dir /etc/etcd/etcd.conf.yml      # 在任一 etcd 节点
```

> 老环境的 `env.yaml` 若是早先生成的精简版（可能缺这几项），按 `tmp/env.yaml.example` 逐项比对补全。注意 `env.yaml` 不入库，改 example 不会回写已生成的 `env.yaml`。

### sandbox_image（pause 镜像）怎么定

pause 是每个 Pod 的基础容器（占网络命名空间），**版本与 k8s 版本绑定**。`sandbox_image` 和 `pause_image_version` **都是 `defaults.yaml` 里的派生变量，正常不用手写**——改 `k8s_version` 一处即可，链路是：

```
k8s_version(env.yaml) → k8s_minor(1.34) → k8s_compat[k8s_minor].pause → pause_image_version → sandbox_image
                                                                          随 is_offline 切: 自建 Harbor / 在线阿里云 mirror
```

1. **查目标 k8s 版本要哪个 pause**（权威，别猜）：
   ```bash
   kubeadm config images list --kubernetes-version v1.34.3 | grep pause
   # 输出如 registry.k8s.io/pause:3.10.1
   ```
   `k8s_compat` 现有行：1.28→`3.9`、1.34→`3.10.1`、1.36→`3.10.2`。

   ⚠️ **表里没有的小版本会静默取兜底值 `3.10.1`，不会报错。** 例如 `k8s_version` 填 `1.32.x` 时表里无 `1.32` 行，pause 会落到 `3.10.1`（1.32 实际要 `3.10`），containerd 的 sandbox 就用错了版本。上新小版本时按 [十四](#升级-k8s-版本-checklist示例-1343--136x) 给 `k8s_compat` 加一行。

2. **离线环境**会自动指向私有 Harbor（外网 `registry.k8s.io` 拉不到）：`sandbox_image` 解析为 `{{ registry }}/pause:{{ pause_image_version }}`，`registry` 见 [十](#十关键变量参考group_varsallenvyaml)。

3. **⚠️ 必须与 kubeadm/kubelet 用的 pause 一致**，否则会拉出两个 pause / kubelet 报镜像不匹配。

## 三、SSH 免密

Ansible 能连上各节点即可跑（连接逻辑见 `connection.yaml`：root 免密直连 / 用户+sudo 回退）。想给控制机建**持久**免密,用下面这对。

### 控制机 → 各节点免密：交付前置 / 交付收尾（add / remove，推荐）

把**控制机（跑 ansible 这台）**的 root 公钥下发到全 `cluster` / 再撤除。控制机通常不在 inventory 里，需单独成对管理：

```bash
# 交付前置：把控制机 root 公钥下发到全 cluster（首次控制机还没免密时加 -k 输密码）
ansible-playbook playbook/add-control-key.yaml -k

# 交付收尾：从全 cluster 撤除控制机 root 公钥
ansible-playbook playbook/remove-control-key.yaml
```

> **`-k` 用不了时（目标机 root 完全禁止直连，只有普通账号能 sudo）**：`-k` 走的仍是 root 密码登录，如果目标机的安全策略是 `PermitRootLogin no`，root 密码再对也连不上。这种场景改用 `connect_as=sudo`，让 `connection.yaml` 的连接逻辑走「普通用户 + sudo」而不是尝试 root 直连：
> ```bash
> ansible-playbook playbook/add-control-key.yaml -e connect_as=sudo
> ```
> 同时要在 `env.yaml` 配好 `bootstrap_user` / `bootstrap_ssh_pass`（及 `bootstrap_become_pass`，未设则回退用 `bootstrap_ssh_pass`）。公钥下发成功后，目标机 root 免密可用，后续 playbook 不用再带这个参数——`connect_as` 默认就是 `root`。

### 单机手动配 root 本机免密（备用）
```bash
ssh-keygen -t rsa -b 4096 -f /root/.ssh/id_rsa -N ""
cat /root/.ssh/id_rsa.pub >> /root/.ssh/authorized_keys
chmod 600 /root/.ssh/authorized_keys
```
> 还没 root 免密 → 在 `env.yaml` 配 `bootstrap_*`，连接自动走「用户 + sudo」；已有 root 免密 → root 直连，无需额外配置。

> **宿主机层跑多机 MPI（一台 launcher → 多台 worker）需要节点间免密时**：复用 `add-control-key.yaml`，把公钥源指到 launcher 节点即可——在 launcher 上 `ansible-playbook add-control-key.yaml -e control_pubkey_file=/root/.ssh/id_rsa.pub`。（k8s 内的多机训练走 pod 网络，不需要宿主机免密；故不再单独维护节点↔节点 N×N 互信脚本。）

> **部署节点（跑 ansible 的控制机）和 first master 不是同一台时，加 master 会报 `sshpass` 相关错误**：`kube-add-master` 里同步证书的任务是 `delegate_to` 到 `first master` 上执行、再由它去 `rsync` 自己的证书给其他 master——也就是需要 **first master 免密登其他 master**，不是控制机登它们。控制机本身对全 cluster 有免密不代表这条链路也通。缺免密时 ansible 会尝试用密码认证兜底，进而调用 `sshpass` 这个外部二进制；控制机没装它就直接报 `[Errno 2] No such file or directory: b'sshpass'`。用 `add-control-key.yaml` 把 first master 的公钥下发给整个 `k8s_master` 组即可修好（把 first master 换成 inventory 里实际那台）：
> ```bash
> ansible-playbook playbook/add-control-key.yaml -e source_node=cpu200 -e target_hosts=k8s_master
> ```
> 装 `sshpass`（`apt-get install sshpass` / `yum install sshpass`）也能让报错消失，但只是让密码认证这条路继续跑，没解决 first master 缺免密的根本问题，换台控制机或重装系统后还会再犯。

- 两者精确互逆，只针对**控制机这一把** key（`lookup` 读控制机本地 `/root/.ssh/id_rsa.pub`）。公钥路径可覆盖：`-e control_pubkey_file=/path/to/id_rsa.pub`。
- ⚠️ `remove-control-key` 是**交付最后一步**：跑完控制机对各节点的免密立即失效，之后再连需要密码。务必在其它 playbook 都跑完后再执行；验证（如 `ansible cluster -m ping`）要趁免密还在时做。

## 四、系统初始化（init.yaml，在线/离线同一入口）

统一走 `init.yaml`，在线/离线由 `group_vars/all/env.yaml` 的 `is_offline` 控制（原来的 `init-offline.yaml` 已删除）：

| is_offline | 用途 |
|---|---|
| `false` | 在线：联网 yum/apt（默认）|
| `true` | **离线**：改用本地 `/opt/*-pkgs` yum/apt 源，按**显式列表**安装（不再整目录 `localinstall`）|

按发行版分流（ubuntu/kylin/openEuler/redhat），公共项在 `common.yaml`。

**离线包 + 下载脚本**（联网机生成）：

| 系统 | 离线包 | 生成脚本 |
|---|---|---|
| Ubuntu | `ios-offline/ubuntu{22,24}_{x86_64,arm64}.tar.gz` | `download_ubuntu_packages.sh` |
| Kylin | `ios-offline/kylin_{x86_64,arm64}.tar.gz` | `download_kylin_packages.sh` |
| openEuler | `ios-offline/openEuler22_{x86_64,arm64}.tar.gz` | `download_openeuler_packages.sh` |

> 脚本 docker 多架构下载，含 k8s 依赖（socat/conntrack/ipset/ebtables/chrony/ipvsadm 等），**并含 haproxy/keepalived**（LB 节点用）。三发行版均生成本地 repo 索引（Ubuntu 的 `Packages`、RPM 的 `repodata/`），init 据此走「本地源 + 显式列表」安装。
>
> **LB 包已并入 ios-offline，不再单独打 lb-offline 包**：haproxy/keepalived 与基础包同在一次依赖解析里下载（公共依赖去重、无重叠），随 ios-offline 一起发。init 的显式列表**不含**这两个，故非 LB 节点只存不装；LB 节点由 `haproxy-ha` 角色从**同一个本地源按名安装**。改 builder 的 `OFFLINE_PKGS` 需同步 init 里对应的 `*_offline_pkgs` 显式列表（不含 LB 那两个）。

**⚠️ ansible 版本兼容**：Kylin V10 SP3 自带 **ansible 2.8.8**，不支持 `ansible.builtin.` FQCN。本仓库已全用**短名**模块，兼容 2.8+。**写新 role 也用短名。**

### 时间同步（chrony）
- **变量 `chrony_ip`**：NTP 服务器 IP（`group_vars/all/env.yaml` 设）
- 模板 `chrony.conf.j2` → Debian `/etc/chrony/chrony.conf`，RHEL 系 `/etc/chrony.conf`
- 服务名：Debian=`chrony`，RHEL/openEuler/Kylin=`chronyd`（自动区分）
- 验证：`chronyc sources`

### 单机快速初始化（不走 ansible）

只有一两台、或临时机器不想起 ansible 时，用 `scripts/` 下的**单机脚本**直接跑，效果等价于 init 角色的**在线**初始化（时区/br_netfilter/sysctl 调优/limits/关 swap/关防火墙+SELinux(RHEL)/装 k8s 基础依赖/chrony）。

| 脚本 | 适用 | 说明 |
|---|---|---|
| `scripts/debian-init.sh` | Debian / Ubuntu | 对齐 `debian.yaml`+`common.yaml`；含 apt 非交互、关自动更新/needrestart、禁 cloud-init 网络接管、hold 当前内核 |
| `scripts/rhel-init.sh` | CentOS/RHEL/Rocky/Alma · Kylin · openEuler | 对齐 `redhat.yaml`/`kylinsp3.yaml`/`openEuler.yaml`+`common.yaml`；按 `/etc/os-release` 自动判族分流装包（`--skip-broken`）；dnf 优先 |

```bash
sudo bash scripts/debian-init.sh                       # 默认(不改主机名, chrony 用系统默认源)
sudo bash scripts/rhel-init.sh   -H k8s-master1        # 顺便设主机名
sudo CHRONY_IP=10.0.0.1 bash scripts/rhel-init.sh      # 指定内网 NTP 上游
```

> - 面向**在线**单机（能直连 apt/yum 源）；**离线批量**仍走 ansible 的 `init.yaml`（在 env.yaml 置 `is_offline=true`，它配好本地 `/opt/*-pkgs` yum/apt 源后按显式列表安装）。
> - sysctl 写 drop-in `/etc/sysctl.d/99-k8s.conf`（比覆盖 `/etc/sysctl.conf` 安全等效）；幂等可重复跑。
> - `rhel-init.sh` 对 openEuler 也统一关了防火墙/SELinux（角色本未做，但对 k8s 节点推荐且幂等安全）。
> - 跑完建议 `reboot` 一次让内核参数/limits 完全生效。

## 五、数据盘挂载

containerd 数据目录入口 = `config.toml` 的 `root`（本仓库变量 `containerd_root`，等同 docker `data-root`）。

路径变量：`container_base` 在 `env.yaml`（group_vars）定义，默认 `/var/lib/container`；`containerd_root` 在 `defaults.yaml` 跟随它（`{{ container_base }}/containerd`），不用单独配。**三个挂盘 playbook 和 `containerd-setup` 都读同一处**，改一个地方全体生效：

```yaml
# env.yaml
container_base: "/data"
```

> 注：`container_base` 的唯一定义处就是 `env.yaml`，`defaults.yaml` 里没有，各 playbook 也不要在自己的 play `vars:` 里重复定义 —— play vars 优先级高于 group_vars，重复定义会让 `env.yaml` 的改动对那个 playbook 静默失效，而 `containerd-setup` 仍按 `env.yaml` 走，两边路径对不上（盘挂在 A、containerd 往 B 写、数据落回系统盘且不报错）。`mount-nvme-lvm-containerfs.yaml` 曾经就这么写过，已改为统一读 group_vars。

```
数据盘 → 挂到 {{ container_base }}(默认 /var/lib/container)
   ├─ containerd/  ← 5.1/5.2 走 config root(不 bind); 5.3 额外 bind 到 /var/lib/containerd
   └─ kubelet/     ← bind 到 /var/lib/kubelet
```

三个 playbook 对应三种场景，**安全边界不一样，选错会清盘**：

| playbook | 适用 | LVM | 对有残留数据的盘 |
|---|---|---|---|
| `mount-nvme.yaml` | 单盘 / 已有 LVM 卷 | 不建 | 只挂不格式化，数据保留 |
| `mount-nvme-lvm.yaml` | 多盘(2或4块) 通用 | `vg_container/lv_container`，用满 VG，64K 条带 | **跳过**，不选中 |
| `mount-nvme-lvm-containerfs.yaml` | 4 块 3.5T 交付标准 | `vg/containerfs`，默认 1.5T（`lv_size` 可改 `100%FREE` 用满），4 路 256K 条带 | **默认 `wipefs -a` 清掉** |

> 👉 **只想知道怎么跑**，直接看 [5.5 完整操作流程](#55-完整操作流程从零到挂好)。下面 5.1–5.4 是各 playbook 的行为与安全边界细节。

### 5.1 mount-nvme.yaml（单盘）

设备写死在 playbook 里（`device_path`，默认 `/dev/nvme2n1`），换盘改这一处。仅当「未挂载 + `blkid` 完全空白」才格式化，再叠加 `force: no` 双保险；盘上有任何文件系统就跳过格式化直接挂载，数据保留。

### 5.2 mount-nvme-lvm.yaml（多盘通用，最保守）

自动识别空闲 NVMe，选盘 6 道检查：无分区 / 无 holders / `blkid` 无签名 / `wipefs` 无残留 / 非 PV / 未挂载。**任何一道不过就跳过该盘，绝不碰有数据的盘。** 组 LVM 前必须**数量为 2 或 4 且容量完全一致**，否则 assert 中止。盘容量不一致时把 `lvm_striped` 设 `false` 走线性。

**盘识别不到 / 数量不够**，通常是盘上有残留签名被第 3、4 道拦下（3.84T 二手盘常见）。**先和同事确认该盘可清**，再手动清盘重跑：
```bash
nvme format /dev/nvme5n1 --ses=1   # ⚠️ 数据全没,务必确认无用
nvme list
```

### 5.3 mount-nvme-lvm-containerfs.yaml（4×3.5T 交付专用）

这个 playbook 是把现场交付的手工命令固化下来的，逐条对应：

```bash
wipefs -a   <4块NVMe>                                  # ← 清签名(受 nvme_wipe_signatures 控制)
pvcreate    <4块NVMe> -y -f                            # ← 创建 PV
vgcreate vg <4块NVMe>                                  # ← 卷组固定叫 vg
lvcreate -n containerfs -L 1.5T -i 4 -I 256 vg -y      # ← 大小由 lv_size 决定,见下
mkfs.xfs -f /dev/mapper/vg-containerfs                 # ← XFS
```

**LV 大小：`lv_size` 一个变量，两种写法都兼容。** 默认 `1.5T`（交付标准），想用满 VG 就改成 `100%FREE`：

| `lv_size` | 实际执行 | 说明 |
|---|---|---|
| `1.5T` / `500G` / `2048M` | `lvcreate -L 1.5T` | 绝对大小，**默认**，VG 里留余量 |
| `100%FREE` / `80%VG` / `50%PVS` | `lvcreate -l 100%FREE` | 百分比，用满（或按比例吃）VG |

```bash
# 默认 1.5T, 不用传任何东西
ansible-playbook playbook/mount-nvme-lvm-containerfs.yaml

# 用满 VG
ansible-playbook playbook/mount-nvme-lvm-containerfs.yaml -e lv_size=100%FREE
```

参数大小写由 `lv_size_flag` 自动派生（值里含 `%` → `-l` 小写，否则 → `-L` 大写）。**这个必须跟着切**：`lvcreate -L` 不接受百分比、`-l` 不接受绝对值，写反了直接报参数错误。所以别自己去改命令，只改 `lv_size` 就行。

按默认的 `1.5T` 走时，4 块盘组完 VG 约 14T，切掉 1.5T 后还剩约 12.5T 空闲——**这是交付方有意留的余量，不是漏配**，别顺手 `lvextend` 吃掉。确实想用满就走上面 `100%FREE` 那条，别手工 extend（下次重跑对不上账）。

> ⚠️ `100%FREE` 配合条带（`-i 4`）时，LV 实际大小会被向下取整到条带边界对齐，通常比 `vgs` 显示的 Free 略小几个 extent，这是正常的。另外用满之后 VG 里不留空间，`pvmove` 换盘和 LVM 快照都做不了——换盘需求较多的场景建议保留默认。

设备路径 `/dev/mapper/vg-containerfs` 和 `/dev/vg/containerfs` 是同一个设备的两种写法，playbook 里用后者，验证时两种都认。

**playbook 有意偏离现场命令的四处**（都是往安全侧改）：

| 现场手工命令 | playbook 的做法 | 为什么 |
|---|---|---|
| 设备名写死（`nvme0`…`nvme3`） | 按容量区间自动识别整盘，不依赖编号连续 | 写死编号最危险：系统盘正好占了 `nvme0n1` 时照抄命令会直接清掉系统盘。playbook 排除有分区/挂载/holders/已是 PV 的盘 |
| `mkfs.xfs -f` 强制格式化 | `filesystem: force: false` | LV 上已有文件系统时不覆盖，重跑不丢数据 |
| 只 `mount`，不管开机顺序 | bind 挂载带 `x-systemd.requires-mounts-for` 并写 fstab | 保证开机时主挂载先就绪，bind 不会挂空目录 |
| 目录用默认权限 | 目录统一 `0711` | 收紧其他用户对容器数据目录的遍历权限 |

⚠️ 如果现场命令里的设备写成 `/dev/nvme0`…`/dev/nvme3`（不带 namespace），那是控制器字符设备，`wipefs`/`pvcreate` 要的是块设备 `/dev/nvme0n1`。playbook 的正则只匹配 `nvme[0-9]+n[0-9]+`，取的是对的那一层。

⚠️ **和 5.2 的关键差别：它会主动清盘。** 选盘时**故意保留**有残留签名的裸盘作为候选（只拦有分区 / 挂载 / holders / 已是 PV 的盘），随后按 `nvme_wipe_signatures`（**默认 `true`**）对候选盘执行 `wipefs -a`。

⚠️ **`-e nvme_wipe_signatures=false` 并不能保护数据。** 后面的 `pvcreate -y -f` 带 `-f`，照样覆盖残留签名，这个开关只是省掉显式 `wipefs` 那一步。唯一可靠的保护是**实跑前先 `--check` 预览一遍选中的盘**（见 [5.4](#54-实跑前的预览与盘点)），确认识别范围就是预期那 4 块。

**选盘按字节数区间匹配**，不看 `lsblk` 的显示字符串：

| 变量 | 默认 | 说明 |
|---|---|---|
| `expected_disk_bytes` | `3840755982336` | 3.84TB 级 NVMe 标称字节数（= 3.493 TiB，lsblk 显示 `3.5T`） |
| `disk_size_tolerance_pct` | `5` | 容差 ±5% → 实际区间 **[3.319, 3.668] TiB** |
| `expected_disk_count` | `4` | 必须正好识别到这么多块 |

区间外的档位（3.2TB=2.911 TiB、7.68TB=6.986 TiB）不会被选中，识别到 0 块后 assert 中止——**这是保护而非故障**。4.0TB（3.639 TiB）会一并落入区间，属同一交付档位，且"所有盘字节数必须完全一致"的校验仍拦得住混插。

换档位（如 7.68TB）时改 `expected_disk_bytes`，并一起调 `lv_size` / `stripe_count`。

> 为什么不用 `lsblk` 的显示字符串：那个值是 util-linux 四舍五入到 1 位小数的结果，既受 locale 小数点符号影响，同一容量级别的不同型号也可能因字节数差异跨到相邻的舍入桶。按字节数比没有这两个问题。

这个 playbook 把 **containerd 和 kubelet 都 bind** 了（`container_binds`）：`{{ container_base }}/containerd` → `/var/lib/containerd`、`{{ container_base }}/kubelet` → `/var/lib/kubelet`。bind 目标和 `containerd_root` 指向同一份数据，config root 那条路径照样成立，只是两条路都通。

幂等：**VG 已存在时跳过磁盘识别、清盘和 PV/VG 创建**，只补齐 LV、文件系统和挂载，重跑安全。

### 5.4 实跑前的预览与盘点

**先用 `--check` 预览**（三个挂盘 playbook 都支持，不会动任何磁盘）：

```bash
ansible-playbook playbook/mount-nvme-lvm-containerfs.yaml --check --diff
```

会跑完选盘、安全拦截、签名盘点并打印结果，然后在第一个破坏性操作（`wipefs`）之前 `end_host` 早停。输出里 `[--check] 预览汇总` 那段直接给出：本次会纳入 LVM 的盘、其中哪些有残留签名会被 `wipefs -a` 清掉。**核对无误后去掉 `--check` 实跑。**

> 实现方式：只读的 `command`/`shell` 任务都带了 `check_mode: false`，破坏性操作前用 `meta: end_host` 早停。
>
> 这是**必须显式做**的事，不是 ansible 默认行为——ansible 在 check 模式下会跳过 `command`/`shell`，被跳过任务的 register 变量里没有 `.rc` / `.stdout`，紧接着的 `set_fact` 会直接报 undefined，**在打印出任何设备列表之前就挂了**。写别的挂盘/清盘 playbook 时记得照做（`roles/os-init/tasks/grub.yaml` 也是这个写法）。
>
> ⚠️ 早停之后的步骤（`lvcreate` / `mkfs` / `mount`）**不在预览范围内**。check 模式下 VG/LV 还不存在，那些步骤本来也做不出有意义的判断。

**跨全集群的只读盘点**（`--check` 逐台跑较慢时用；全是只读命令，可放心在生产跑）：

```bash
# 1. 每台的块设备树: 分区/LVM/RAID 都会作为子设备显示出来, 先看整体格局
ansible cluster -m shell -a 'lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINT'

# 2. 逐块盘点 NVMe 整盘, 输出 5.3 选盘用到的全部判据(纯只读, 不改任何东西)
ansible cluster -m shell -a 'for d in $(lsblk -dpno NAME | grep -E "nvme[0-9]+n[0-9]+$"); do b=$(basename $d); sz=$(lsblk -dnpo SIZE $d | xargs); by=$(lsblk -bdno SIZE $d | xargs); parts=$(lsblk -nrpo NAME $d | tail -n +2 | wc -l); mnt=$(lsblk -dnpo MOUNTPOINT $d | xargs); hold=$(ls /sys/block/$b/holders 2>/dev/null | wc -l); sig=$(wipefs --noheadings $d | tr "\n" " "); echo "$d size=$sz bytes=$by parts=$parts mnt=[$mnt] holders=$hold sig=[$sig]"; done'

# 3. 已有 LVM/PV 盘点(确认没有正在用的卷组会被撞上)
ansible cluster -m shell -a 'pvs; echo ---; vgs; echo ---; lvs'
```

> 这几条要 root（`wipefs`/`pvs`/`vgs`/`lvs`）。默认 `connect_as=root` 或 `sudo` 时 `connection.yaml` 已经处理好；若绕开了那套逻辑，自己加 `-b`。

**怎么读第 2 步的输出** —— 5.3 只会挑**同时满足**这 5 条的盘（对应 [mount-nvme-lvm-containerfs.yaml:77-82](../playbook/mount-nvme-lvm-containerfs.yaml#L77-L82)）：

`bytes` 落在 **[3648718183219, 4032793781452]** 区间内 **且** `parts=0` **且** `mnt=[]` **且** `holders=0` **且** 不在第 3 步的 `pvs` 列表里。

注意 `sig` **不参与选盘**，它只决定选中之后要不要执行 `wipefs`：

- 选中 + `sig` 非空 → **`wipefs -a` 清掉签名**（这就是会丢数据的那条路）
- 选中 + `sig=[]` → 裸盘，跳过 wipefs，直接 `pvcreate`
- 任一条不满足 → 该盘不被选中，playbook 完全不碰它

**逐台核对满足全部 5 条的盘正好是预期那 4 块，再实跑。**

**其它：**

- 换物理盘：单盘改 `device_path`；LVM 内换盘用 `pvmove`。
- 改数据落盘位置：改 `env.yaml` 的 `container_base` 即可，三个挂盘 playbook 和 `containerd-setup` 都跟着走，`containerd_root` 自动跟随。

### 5.5 完整操作流程（从零到挂好）

以 **4×3.84TB 交付机型 + containerfs** 为主线。另外两个 playbook 的差异见末尾。

#### 第 0 步：inventory 与 env.yaml

`inventory/hosts` 已 gitignore，新环境要先建：

```bash
cp tmp/hosts.example inventory/hosts
vim inventory/hosts
```

机器本体写在 `[cluster]`，再**按盘的形态**放进 `[nvme_single]` 或 `[nvme_lvm]`（只列主机名）——挂盘 playbook 的 `hosts` 就是这两个组：

```ini
[cluster]
cpu-001 ansible_host=192.168.1.111
gn-64-1 ansible_host=192.168.1.121 accelerator_type=nvidia

[nvme_single]
cpu-001            # 单盘 -> mount-nvme.yaml

[nvme_lvm]
gn-64-1            # 多盘组 LVM -> mount-nvme-lvm.yaml / -containerfs.yaml
```

> 组留空时对应的 playbook 匹配不到主机、直接跳过，不会误挂/误清盘。分组理由见 [5.6](#56-gpu--cpu-用不同挂载目录)。

`env.yaml` 若还没生成：`cp tmp/env.yaml.example inventory/group_vars/all/env.yaml`（或跑 `./init.sh`）。挂盘这步只用到 `container_base`，默认值不用改。

确认连得上：

```bash
ansible cluster -m ping
```

#### 第 1 步：`--check` 预览（不动任何磁盘）

```bash
ansible-playbook playbook/mount-nvme-lvm-containerfs.yaml --check --diff
```

看 `[--check] 预览汇总` 那段输出：

```
本次会纳入 LVM 的盘(4 块): ['/dev/nvme0n1', '/dev/nvme1n1', '/dev/nvme2n1', '/dev/nvme3n1']
设备 / 残留签名: [['/dev/nvme0n1', 'LVM2_member'], ['/dev/nvme1n1', ''], ...]
nvme_wipe_signatures=True (注意: 即使置 false, 后面 pvcreate -y -f 仍会覆盖签名)
核对无误后去掉 --check 实跑。
```

**必须核对两件事**：

1. 盘列表正好是预期那 4 块；
2. 签名非空的盘（会被 `wipefs -a` 清掉）确认可清 —— **先和同事确认**。

跑到 `wipefs` 之前就 `end_host` 停了，五个破坏性操作一个都不会执行。

**识别到 0 块然后中止**：看 fail_msg 里的字节区间。多半是盘不在 3.84TB 档位（要改 `expected_disk_bytes`），或盘上有分区 / 挂载 / 已是 PV（那是保护，别硬绕）。

#### 第 2 步：实跑

```bash
# 默认 1.5T LV（交付标准，VG 里留余量）
ansible-playbook playbook/mount-nvme-lvm-containerfs.yaml

# 或：用满 VG
ansible-playbook playbook/mount-nvme-lvm-containerfs.yaml -e lv_size=100%FREE
```

⚠️ **这一步会 `wipefs` 清盘，没有二次确认。** 第 1 步的核对不能跳。

单台先行（在组的基础上再收窄）：

```bash
ansible-playbook playbook/mount-nvme-lvm-containerfs.yaml --limit gn-10-14-64-1 --check --diff
ansible-playbook playbook/mount-nvme-lvm-containerfs.yaml --limit gn-10-14-64-1
```

> 本 playbook 的 `hosts` 是 **`nvme_lvm`**（不是 `cluster`），所以只作用于你显式放进该组的机器——组留空时直接跳过、不会误清盘。给已交付集群加节点时，**新机器加进 `[nvme_lvm]` 后仍建议叠加 `--limit 新节点`**：老节点 VG 已存在会走幂等分支（跳过选盘清盘），但没必要让它们重跑。参见 [十五](#十五扩缩容与卸载节点--etcd--底座) 里 `--limit` 的说明。

#### 第 3 步：验证

```bash
ansible cluster -m shell -a 'lvs -o lv_name,lv_size,stripes,stripe_size vg'
ansible cluster -m shell -a 'findmnt /var/lib/container; findmnt /var/lib/containerd; findmnt /var/lib/kubelet'
```

- `stripes` 应为 `4`、`stripe_size` 应为 `256.00k`；
- 三个挂载点都要在，且已写入 fstab（playbook 用 `mount: state=mounted`，挂载与 fstab 一起做）。

用了 `100%FREE` 时 `lv_size` 会比 `vgs` 的 Free 略小几个 extent —— 条带边界对齐，正常。

#### 第 4 步：接着装 containerd

**顺序不能反，先挂盘再装 containerd**，否则数据会落到系统盘：

```bash
ansible-playbook playbook/containerd-setup.yaml
```

#### 换用另外两个 playbook

```bash
# 单盘 / 盘上已有数据要保留
ansible-playbook playbook/mount-nvme.yaml -e device_path=/dev/nvme2n1

# 多盘但容量不在 3.84TB 档位, 或绝对不想清盘
ansible-playbook playbook/mount-nvme-lvm.yaml
```

`mount-nvme-lvm.yaml` 对容量没有预期值（只要求选中的盘彼此字节数一致、数量 2 或 4），LV 用满 VG。代价是只挑**完全空白**的盘，现场带残留签名的盘一块都不选。这两个也都支持 `--check` 预览。

> **一批机器里盘的形态不一样**（有的 4 盘、有的单盘）时，用 inventory 的 `[nvme_lvm]` / `[nvme_single]` 两个组分开跑，别一条命令打全集群 —— 见 [5.6](#56-gpu--cpu-用不同挂载目录)。

### 5.6 GPU / CPU 用不同挂载目录

默认全集群共用一个 `container_base`。要按机型分开（如 GPU 挂 `/data/gpu-container`、CPU 挂 `/var/lib/container`），下面三种写法都行。

> ⚠️ **先说不能用的那种**：`inventory/hosts` 里写 `[gpu:vars]` + `container_base=...` **不生效**。inventory 文件里的组变量优先级**低于** `group_vars/` 目录，会被 `group_vars/all/env.yaml` 那一行盖掉，而且是**静默**盖掉，不报错。这和 [一](#一主机清单inventoryhostsini-格式) 里「写在 `[all:vars]` 会被 env.yaml 覆盖」是同一个坑。

相关优先级（从低到高）：

```
inventory 文件里的 [组:vars]  <  group_vars/all/  <  group_vars/<组名>  <  inventory 行内 host 变量  <  -e
```

#### 方案一：`group_vars/<组名>` 文件（推荐，尤其当两类机型参数差异不止目录）

新建 `inventory/group_vars/gpu.yaml`：

```yaml
# GPU 节点专用。group_vars/<组名> 优先级高于 group_vars/all/, 故覆盖 env.yaml 的值。
container_base: "/data/gpu-container"
# 两类机型的挂盘参数差异也可以一起放这里, GPU 那套集中在一个文件:
lv_size: 100%FREE
stripe_count: 4
```

`group_vars/all/env.yaml` 里保持 CPU 的默认值不动。前提是 inventory 的 `[gpu]` 组里填了 GPU 机器（`hosts.example` 里该组默认是空的）。

> `group_vars/gpu.yaml` **会入库**（只有 `group_vars/all/env.yaml` 在 `.gitignore` 里）。所以别往它塞密码类字段；纯路径/参数没问题，入库反而便于跨站点复用。

#### 方案二：inventory 行内变量（就几台特殊机器时最直接）

```ini
[cluster]
cpu-001  ansible_host=192.168.1.111
gpu-001  ansible_host=192.168.1.121  accelerator_type=nvidia  container_base=/data/gpu-container
```

行内 host 变量优先级高于所有 `group_vars`，一定生效。机器多了 inventory 会变长。

#### 方案三：按 `accelerator_type` 自动派生（零额外配置）

不新建组、不改 inventory，直接在 `env.yaml` 写条件表达式——复用 GPU 机器本来就要填的 `accelerator_type`：

```yaml
container_base: "{{ '/data/gpu-container' if (accelerator_type | default('none')) in ['nvidia','dcu','npu'] else '/var/lib/container' }}"
```

思路与 [十三.1](#十三1-calico-双-ippoolgpu--cpu-分-pod-网段可选默认关) 的双 IPPool 判定一致（那边也是按 `accelerator_type` 分 gpu/cpu）。代价是 `env.yaml` 里出现逻辑而非纯值；想覆盖单台仍需行内变量。

#### 怎么跑

**目录不同、挂盘方式相同** —— 一次跑完，每台机器各自解析自己的 `container_base`：

```bash
ansible-playbook playbook/mount-nvme-lvm-containerfs.yaml --check --diff
ansible-playbook playbook/mount-nvme-lvm-containerfs.yaml
```

**连挂盘方式也不同**（多盘组 LVM、单盘直挂）—— 在 inventory 里按**盘的形态**分两个组（`hosts.example` 已带这两个组），挂盘时 `--limit` 指定：

```ini
[nvme_lvm]
gn-10-14-64-1        # 4 块同容量, 走 containerfs

[nvme_single]
cn-10-14-72-1        # 单盘
cn-10-14-72-2
cn-10-14-72-3
```

```bash
# 多盘组 LVM
ansible-playbook playbook/mount-nvme-lvm-containerfs.yaml --limit nvme_lvm --check --diff
ansible-playbook playbook/mount-nvme-lvm-containerfs.yaml --limit nvme_lvm

# 单盘
ansible-playbook playbook/mount-nvme.yaml --limit nvme_single -e device_path=/dev/nvme0n1 --check --diff
ansible-playbook playbook/mount-nvme.yaml --limit nvme_single -e device_path=/dev/nvme0n1
```

> **为什么按盘的形态分组，而不是按 `accelerator_type` 自动判断**：盘的数量/容量与有没有 GPU 卡**没有必然关系**——CPU 机也可能 4 盘、GPU 机也可能只 1 块盘。用 `accelerator_type` 推断挂盘方式，换个机型就错。而且清盘这种操作，判断依据越显式越好：`--limit nvme_lvm` 一眼能看出要动哪几台，自动判断则要先在脑子里算一遍匹配结果。
>
> 组留空时那条命令匹配不到主机、直接跳过，不会误跑。以后出现「CPU 机也是 4 盘」，把它加进 `[nvme_lvm]` 即可，不用纠结它算 GPU 还是 CPU。

盘符不统一时不用拆更多组，写在 `[cluster]` 的机器行上（行内变量优先级最高）：

```ini
[cluster]
cn-10-14-72-1 ansible_host=10.14.72.1 device_path=/dev/nvme0n1
cn-10-14-72-2 ansible_host=10.14.72.2 device_path=/dev/nvme1n1
```

#### 两个必须保持一致的点

1. **`containerd-setup` 要和挂盘看到同一个值。** 它也读 `container_base`（自身不带 play vars），所以值来自 `group_vars` 或行内变量时两边自动一致。
   ⚠️ 但用 `-e container_base=...` 传时，**挂盘和 `containerd-setup` 两条命令都得传**——漏一条就会「盘挂在 A、containerd 往 B 写、数据静默落回系统盘且不报错」。这也是推荐方案一/二/三而非 `-e` 的原因。
2. **别在 playbook 的 `vars:` 里定义 `container_base`。** play vars 优先级高于 group_vars，会让你的分组配置对那个 playbook 静默失效（`mount-nvme-lvm-containerfs.yaml` 曾经就这么写过，已改为统一读 group_vars）。

`containerd_root` 是 Jinja 表达式、**逐台求值**，会自动跟成各自的 `<container_base>/containerd`，不用单独配。

## 七、Docker 与 Harbor

**定位**：docker 只给 Harbor 用；k8s 节点用 containerd 直连，不用 cri-dockerd。

- **docker 复用已有 containerd**：docker role 检测到节点已装 containerd 时不覆盖，让 dockerd 通过 `--containerd /run/containerd/containerd.sock` 连现有的（一节点一个 containerd）。**所以先装 containerd 再装 docker。**
- **Harbor**：`ansible-playbook playbook/harbor-install.yaml`（`hosts: harbor`）。
- **域名解析**：`containerd_setup` / `docker-daemon` / `docker-gpu` 三处已统一 include `playbook/tasks/ensure-harbor-hosts.yml`（harbor 解析的唯一写入方，会顺带清掉历史 marker `# Ansible inventory hosts` 写下的重复块）。`trust-harbor-ca` 也 include 同一个任务，因为它可能跑在那三个角色**之前**（全新节点先信任 CA 再装运行时），那时解析还不存在，TLS 探针会因「域名解析不了」而报 FAILED，与 CA 无关却极易误判成证书问题。
- **CA 信任**：`ansible-playbook playbook/harbor-trust.yaml`（`hosts` 是 `docker:containerd`，只对会拉/推镜像的节点装 CA；按机器上实际存在的 CA 目录判发行版，不靠发行版名字匹配），完后 `docker login harbor.local.clusters -uadmin -pHarbor12345` 验证。

  ⚠ **只在 harbor 证书被重新签发后才需要跑它**。CA 在 harbor 首次安装时生成一次（`harbor/tasks/ssl.yaml` 每个生成任务都带 `creates:` 守卫，之后重跑 `harbor-install` 不会动它），所以平时不用管。本 playbook 分发的是**运行那一刻** harbor 上的 CA——是快照，不是订阅。重签证书后旧的分发即刻作废，全集群会报 `x509: certificate signed by unknown authority ... crypto/rsa: verification error`（注意这不是「缺 CA」，是「装的是上一代 CA、验不过签名」）。此时重跑本 playbook，**跑完还要重启 docker**：

  ```bash
  ansible docker:containerd -b -m shell -a "systemctl restart docker"
  ```

  dockerd 是长驻进程，系统证书池在进程内只加载一次并缓存，不重启读不到新 CA——会出现「openssl 验证通过、docker push 却报 unknown authority」的矛盾现象。`daemon.json` 里有 `live-restore: true`，重启 dockerd 不会停掉正在跑的容器。
  验证不通时看 `Report TLS trust result` 那条的 `KEY=VALUE`：`RESOLVE` 空或 `CONNECT_ERR` 有值＝解析/网络；`FINGERPRINT` 与 `EXPECT_FP` 不一致＝本机装的是上一代 CA；`VERIFY_ERR=num=20`＝CA 在但 bundle 没重建。默认不中断，要它变红加 `-e harbor_trust_strict=true`。

Harbor/Docker 变量见 [十](#十关键变量参考group_varsallenvyaml)。

二选一：

| 方案 | playbook / hosts | 组成 |
|---|---|---|
| **haproxy-ha** | `lb-haproxy-install.yaml`，`hosts: k8slb` | haproxy(`:{{ apiserver_lb_port }}`) → master `:{{ apiserver_port }}` + keepalived VIP |

keepalived：动态 priority（节点序）+ nopreempt + VIP 派生 router_id/auth_pass + 健康检查脚本触发漂移。

```bash
ansible-playbook playbook/lb-haproxy-install.yaml   # 或 playbook/lb-nginx-install.yaml

## 十二、Kubernetes 部署（etcd → 控制面 → CNI → worker）

> 前提：底座已就位（[快速上手](#快速上手命令清单)）——各节点已装 **containerd**、已配 **免密**、Harbor 可用（离线时）。
> 在线/离线：默认在线；**离线整条链路加 `-e is_offline=true`**。

主机清单需有这些组（见 [一](#一主机清单inventoryhostsini-格式)与 `tmp/hosts.example`）：`[etcd]`、`[k8s_master]`、`[k8s_node]`。

> **单 master 免 LB**：只放 1 台 `[k8s_master]`、**不设 `lbvip`** 即可，跳过 haproxy/nginx-ha。省机器可把该 master 也写进 `[etcd]` 与 etcd 共机。
> `controlPlaneEndpoint` 现在**无条件写**（无 VIP 时取「首 master : `apiserver_port`」），所以单 master 集群以后也能加 master。
> ⚠ **2026-09-16 之前建的单 master 集群不适用**：那时 kubeadm 省略了该项，而它写进 ConfigMap 与证书 SAN、**事后不可改** —— 加 master 会被 kubeadm 的 preflight 拒绝（`unable to add a new control plane instance to a cluster that doesn't have a stable controlPlaneEndpoint address`），只能重建集群，或手工改 ConfigMap + 重签 apiserver 证书 + 更新每节点四份 kubeconfig（本仓库无对应工具）。用 `kubectl -n kube-system get cm kubeadm-config -o yaml | grep -i controlPlaneEndpoint` 查有没有。
> 另注：无 VIP 时 endpoint 指向首 master 自己，**入口仍是单点**（首 master 挂了其余 master 联系不上），只是不再堵住「以后加 master」这条路。真 HA 仍需 VIP 或外部 LB。
> **多 master 高可用**：配 `lbvip` + 跑 LB（[八](#八负载均衡k8s-apiserver-高可用haproxy--nginx-ha--keepalived)）。不配 `lbvip` 时 `k8s-install` 预检会拦下 —— 但拦的理由是**入口为单点、不是真 HA**，不是"建不出来"（`controlPlaneEndpoint` 无条件写，join 能过）。明知单点仍要继续：`-e allow_multi_master_without_lb=true`。
>
> **LB 与 master 共机就能做真 HA，不需要额外机器。** haproxy 前端听 `apiserver_lb_port`（默认 8443）、后端指向各 master 的 `apiserver_port`（6443），同机不冲突；VIP 在几台 master 间浮动，某台挂了 keepalived 把 VIP 漂走、那台的 haproxy 转发到还活着的 apiserver，入口不断。`[k8slb]` 直接填 master 主机名即可。
> ⚠ **顺序：先 LB 再建集群。** `admin.conf` 的 server 指向 `VIP:apiserver_lb_port`，init 之后一堆 task 靠 kubectl，VIP 不通会卡住。即 `lb-haproxy-install.yaml` → `k8s-install.yaml`。
> ⚠ 全新共机部署有个冷启动窗口：keepalived 的健康检查只看 haproxy 在不在听（`ss -lntp | grep -q haproxy`），不管后端通不通，所以 haproxy 先起来、VIP 先上，而后端要等 `kubeadm init` 拉起 apiserver 后由 `check inter 5s rise 2` 标 up（约 10 秒）。中间可能短暂 503，卡住重跑一次即过。
>
> **master 台数与 etcd 台数是两回事，别混。** apiserver 无状态，2 台 master + VIP 就是真 HA；**要 3 台以上是 etcd 的要求**（quorum 需过半，2 台要 2/2 —— 挂任一台就停写，比单台还脆）。所以：
> · etcd 与 master 共机（`[etcd]` = `[k8s_master]`）→ master 就得 **3 台起、奇数**；
> · etcd 独立 3 台 → master 2 台也是真 HA。
> 仓库对 etcd 台数**没有台数校验**（只有 `etcd-scale-down.yaml` 拦"删到少于 2 台"），奇数是 `tmp/hosts.example:36` 的建议而非强制 —— 自己把住。
>
> **1 master 起步、以后扩到 3 台**是可行的（`10c1ccd` 之后 endpoint 无条件写，不必重建）：`[k8s_master]` 加机器后跑 `k8s-add-master.yaml`。但注意它**完全不碰 etcd**，共机场景下 etcd 仍是 1 台 —— etcd 扩容要另跑 `etcd-scale-up.yaml`（把新节点列进 `[etcd_to_add]`）。另外此时 endpoint 已定为「首 master:6443」，补 VIP 需要改 ConfigMap + 重签 apiserver 证书 + 更新每节点四份 kubeconfig（本仓库无对应工具），所以**打算做 HA 就一开始带上 `lbvip`**。

```bash
# 1. 部署外置 etcd 集群(建议 3/5 台奇数)
ansible-playbook playbook/etcd-deploy.yaml                       # 离线加 -e is_offline=true

# 2. 安装控制平面(首 master kubeadm init + CNI + 其余 master 加入)
ansible-playbook playbook/k8s-install.yaml                      # 离线加 -e is_offline=true
#    分步做也可(等价):
#      k8s-init-master.yaml  只对【第一台 master】(kubeadm init + CNI + nodelocaldns)
#      k8s-add-master.yaml   其余 master 加入(内部先跑 kube-common 装二进制/配 kubelet)

# 3. 加入 worker 节点
ansible-playbook playbook/k8s-add-node.yaml                     # 离线加 -e is_offline=true

# 4. 验证
kubectl get nodes                # 全部 Ready
kubectl get pod -A               # coredns / CNI Pod Running
```

**内部机制**：
- **etcd**：外置二进制 + systemd，`certs` role 用 openssl 生成 CA / 每节点证书 / apiserver-etcd-client 证书。
  > **直接用 etcdctl**：部署时已把 `etcdctl` 软链到 `/usr/local/bin` 并在 `/etc/profile.d/etcdctl.sh` 导出端点与证书环境变量。登录任一 etcd 节点即可**零参数**操作（新开 SSH 自动生效；当前会话先 `source /etc/profile.d/etcdctl.sh`）：
  > ```bash
  > etcdctl endpoint health                    # 各成员健康
  > etcdctl member list -w table               # 成员列表
  > etcdctl endpoint status --cluster -w table # leader / DB 大小 / 版本
  > ```
- **控制面**：kubeadm + external etcd；有 `lbvip` 时 `controlPlaneEndpoint={{ lbvip }}:{{ apiserver_lb_port }}`（HA）。`kubeadm-config.yaml.j2` 的 `imageRepository`、`kubernetesVersion`、端口均取变量（不再硬编码）。
- **镜像**：离线先 `docker load` 本地 tar 推 Harbor（`sync-images-to-harbor` / `sync-cni-images`，仅离线跑）；在线直接从公共 mirror 拉，跳过同步。
- **k8s 二进制**：离线从 `offline/artifacts/kubernetes/v{版本}/bin/{arch}/`；在线从 `k8s_bin_mirrors`（复数，多源失败自动切换）下载。

## 十三、CNI 切换（calico / flannel / cilium）

KubeKey 风格：**一个变量 `kube_network_plugin`** 决定装哪个（`roles/cni` 调度）。默认 `calico`。

| 插件 | 方式 | 说明 |
|---|---|---|
| `calico` | manifest（`kubectl apply`） | BGP，pod CIDR 继承 kubeadm `podSubnet` |
| `flannel` | manifest | vxlan，`net-conf.json` 的 `Network` 取 `pod_subnet` |
| `cilium` | helm chart | eBPF，`ipam=cluster-pool`；默认保留 kube-proxy、关 hubble |

```bash
# 安装时选(在 env.yaml 或 -e 指定)
ansible-playbook playbook/k8s-install.yaml -e kube_network_plugin=flannel

# 已装好的集群单独装/切 CNI(首 master 执行)
ansible-playbook playbook/k8s-cni.yaml -e kube_network_plugin=cilium
```

> ⚠️ **`k8s-cni.yaml` 只 apply,不删旧 CNI**——用于全新集群装 CNI、或清掉旧 CNI 后装新的。
> **在已装 CNI 的集群上原地换**，用 `k8s-cni-switch.yaml`（删旧 → 清节点 → 装新 → 重建 coredns）：
> ```bash
> ansible-playbook playbook/k8s-cni-switch.yaml -e kube_network_plugin=flannel -e confirm_switch=yes
> ```
> 会短暂中断网络;业务 Pod 需自行 `kubectl rollout restart`。**最干净的换法仍是 reset 重装。**
> 不要在同一集群混装多个 CNI。`cilium` 需 helm（离线内置 `offline/artifacts/helm/`,在线自动下载）。
> 可选叠加 multus:`-e enable_multus=true`。

### 十三.0 多网卡节点：`calico_ip_autodetection_method`

calico-node 要探测本机 IP 作为 BGP 对端地址与隧道源地址。默认 `first-found`（calico 上游默认）——**按网卡顺序取第一个非本地地址**。

⚠️ **多网卡机器上这很容易挑错**，挑到管理网或存储网去。症状是跨节点 Pod 不通、或流量走错网卡跑；而 kubelet 那层已经用 `kube_node_ip` 钉成了 `ansible_host`（见 [十](#十关键变量参考group_varsallenvyaml)），**两层不一致时症状很像「CNI 没装好」**，排查费劲。

多网卡站点建议在 `env.yaml` 设成跟随 Node InternalIP，两层自动对齐：

```yaml
calico_ip_autodetection_method: kubernetes-internal-ip
```

| 取值 | 含义 |
|---|---|
| `first-found` | **默认**，按网卡顺序取第一个非本地地址（多网卡易挑错） |
| `kubernetes-internal-ip` | 跟随 Node 的 InternalIP（= kubelet 上报、被 `kube_node_ip` 钉死的那个）**推荐** |
| `interface=bond0` | 指定网卡名，支持正则如 `interface=eth.*` |
| `can-reach=10.14.64.1` | 探测「能到达某地址」时用的那张网卡 |
| `cidr=10.14.64.0/24` | 取落在该网段内的地址 |

**装之前先确认挑对了**：

```bash
# 各节点的 InternalIP(kubelet 上报)
kubectl get node -o custom-columns=NAME:.metadata.name,INTERNAL-IP:.status.addresses[?\(@.type==\"InternalIP\"\)].address

# calico 实际选中的地址(装完后对比, 两边应一致)
kubectl get node -o custom-columns=NAME:.metadata.name,\
CALICO-IP:.metadata.annotations.projectcalico\\.org/IPv4Address
```

> ⚠️ **改这个值会让 calico-node 重启并重新选址。** 已跑起来且当前挑对了的集群不要动——默认值保持 `first-found` 就是为了不改变现网行为。

### 十三.1 Calico 双 IPPool（GPU / CPU 分 Pod 网段，可选，默认关）

**默认 `calico_dual_ippool_enabled: false`，行为与原来完全一致**（calico 按 `podSubnet` 自建单个默认池），现有集群不受影响。只在需要按硬件类型隔离 Pod 网段时才开。

开启后有两处变化：calico-node 加 `NO_DEFAULT_POOLS=true`（不再自建默认池，否则会和手建的池抢占），另外渲染出 `calico-ippools.yaml` 并**在主 manifest 之后单独 apply** 两个 IPPool 资源 `gpu-pool` / `cpu-pool`。

> **为什么要分两次 apply**（`roles/cni/tasks/calico.yaml` 里第 4-6 个任务）：两个 IPPool 是**使用** `ippools` CRD 的自定义资源，而该 CRD 定义在主 manifest 里。放同一个文件 `kubectl apply` 会撞 apiserver 的异步注册竞态——CRD 本身创建成功了，但注册进 discovery 缓存需要时间，kubectl 推进到文件末尾时还查不到这个 kind：
>
> ```
> resource mapping not found for name: "gpu-pool" ... no matches for kind "IPPool"
> in version "crd.projectcalico.org/v1"; ensure CRDs are installed first
> ```
>
> **全新集群首次开双池必踩**（重跑一次就好，因为那时 CRD 已就绪）。单池模式主 manifest 里没有任何 CR，所以这个缺陷此前一直没暴露。现在的顺序是 `apply 主 manifest` → `kubectl wait --for condition=established crd/ippools...`（90s 超时）→ `apply calico-ippools.yaml`，不再需要人工重跑。

```yaml
# env.yaml —— 四项一体, 缺一不可
calico_dual_ippool_enabled: true
calico_gpu_pool_cidr: "10.14.32.0/19"    # GPU 段, 自己规划
calico_cpu_pool_cidr: "10.14.96.0/20"    # CPU 段, 自己规划
pod_subnet: "10.14.0.0/17"               # ⚠ 必须回头改! 覆盖上面两段的超网(算法见下)
service_subnet: "10.96.0.0/12"           # 与上面三段都不重叠即可
```

> ⚠️ **最容易漏的是 `pod_subnet`。** 它在 `env.yaml` 里位于双池块**上方**十几行，而人是在双池块处删注释的，删完不会回头看。只开双池、`pod_subnet` 留着默认值，装出来的集群**能跑但是错的**：Pod 从池段取地址，而 kube-proxy 的 `clusterCIDR` 来自 kubeadm 的 `podSubnet`（= `pod_subnet`），于是 nftables/iptables 里那句 `saddr != <clusterCIDR> jump mark-for-masquerade` 对**所有** Pod 成立 —— Pod 访问任何 ClusterIP 都被 SNAT 成节点 IP：
>
> - 后端拿不到真实源 Pod IP；
> - 按源 Pod / 命名空间选择器写的 NetworkPolicy 对经 Service 的流量失效；
> - 多一层 SNAT + conntrack，高并发下有端口耗尽风险。
>
> **连通性完全正常**，所以 ClusterIP / NodePort / DNS 功能测试全过也发现不了。2026-09-17 现网踩过（`pod_subnet` 留着默认的 `10.240.0.0/12`，两池是 `10.14.32.0/19` + `10.14.96.0/20`）。而 `pod_subnet` 建完集群不可改，只能改 kube-proxy 的 cm 兜（见 [十七、常见问题排查](#十七常见问题排查)），所以必须在装机**之前**改对。现在 `roles/cni/tasks/calico.yaml` 有预检会拦住，见下文。
>
> 顺带：CIDR 别写主机位非零的形式。`10.244.0.0/12` 会被掩码归一成 `10.240.0.0/12` —— 能用，但你在 nft 规则里看到的是归一后的值，和 `env.yaml` 里写的对不上，排查时容易怀疑错方向。预检会对此发警告。

⚠️ **`pod_subnet` 在双池模式下仍然必填，不能注释掉。** 它喂给 kubeadm 的 `networking.podSubnet`（进而是 kube-controller-manager 的 `--cluster-cidr`），空着 kubeadm 会拒绝。开双池只是让 **calico 不再用它自建默认池**（`NO_DEFAULT_POOLS=true`），实际分池改由两个 IPPool 决定——它不再决定分池，但**不等于可以不填**。另外它也被 role 内预检 assert 拦着（见 [二 · 四个必填项](#四个必填项defaultsyaml-故意不兜底)）。

| 变量 | 默认 | 说明 |
|---|---|---|
| `calico_dual_ippool_enabled` | `false` | 总开关 |
| `calico_gpu_pool_cidr` / `calico_cpu_pool_cidr` | `""` | **开启时必填**，预检校验非空+格式+掩码合法+重叠+`pod_subnet` 覆盖关系 |
| `calico_gpu_pool_blockSize` | `28` | 每块 16 个地址 |
| `calico_cpu_pool_blockSize` | `26` | 每块 64 个地址 |

#### `pod_subnet` 超网怎么算

两个池段**不要求连续**，但 `pod_subnet` 必须是能同时覆盖它们的超网。不连续时不能靠"合并"得出，只能逐级放大前缀去试。以一套实际规划为例：

```yaml
calico_gpu_pool_cidr: "10.14.32.0/19"    # 10.14.32.0  - 10.14.63.255
calico_cpu_pool_cidr: "10.14.96.0/20"    # 10.14.96.0  - 10.14.111.255
```

中间隔着 `10.14.64.0/19`，两段合不成一个块。逐级试：

| 候选 | 覆盖两段 |
|---|---|
| `10.14.32.0/20` | ❌ |
| `10.14.32.0/19` | ❌ |
| `10.14.0.0/18` | ❌ |
| **`10.14.0.0/17`** | ✅ 最小可用 |

```yaml
pod_subnet: "10.14.0.0/17"               # 10.14.0.0 - 10.14.127.255, 两段都在内
service_subnet: "10.206.0.0/16"          # 与两个池段都不重叠
```

超网里没被池占用的部分（本例是 `10.14.0.0/19` 与 `10.14.64.0/19`）不会被 calico 使用（`NO_DEFAULT_POOLS=true` 之下它不碰超网空闲段），留着以后加池正好。

用 Python 快速验算（自己的网段代入即可）：

```bash
python3 -c "
import ipaddress as ip
gpu=ip.ip_network('10.14.32.0/19'); cpu=ip.ip_network('10.14.96.0/20')
svc=ip.ip_network('10.206.0.0/16')
print('GPU/CPU 重叠:', gpu.overlaps(cpu))
print('GPU/SVC 重叠:', gpu.overlaps(svc), ' CPU/SVC 重叠:', cpu.overlaps(svc))
for p in range(20,14,-1):
    c=ip.ip_network('%s/%d'%(gpu.network_address,p), strict=False)
    if c.supernet_of(gpu) and c.supernet_of(cpu): print('最小超网:', c); break
"
```

**三段两两都不能重叠**：GPU 池 / CPU 池 / `service_subnet`，另外也别撞上 LB VIP 与 ApiServer 网段。

#### blockSize 决定的是"每节点拿多少地址"，不是节点数

calico **按块分配**：节点上 Pod 数超过一块容量就再申请一块。所以：

```
可容纳节点数 = 池内块数 / ceil(每节点 Pod 数 / 每块地址数)
```

「块数」本身**不等于**可容纳节点数。以上面那套规划为例（`kubelet_max_pods` 默认 **110**）：

| 池 | blockSize | 每块地址 | 池内块数 | 每节点 16 Pod | 每节点 110 Pod |
|---|---|---|---|---|---|
| GPU `/19`（8192 地址） | `/28` | 16 | 512 | 512 节点 | **73 节点**（每节点 7 块） |
| CPU `/20`（4096 地址） | `/26` | 64 | 64 | 64 节点 | **32 节点**（每节点 2 块） |

所以「`/28` 可满足 512 个节点」这类说法，**前提是每节点 Pod 数不超过一块的容量**（16 个）。规划时按**实际每节点 Pod 数**算：

- **GPU 节点**：Pod 数通常不多（一个训练任务常占整机），`/28` 够用。但**别忘 DaemonSet**——监控、日志、CNI、device-plugin 这些每台都有，很容易吃掉 16 个里的一半以上。先数一下自己集群的 DaemonSet 数量。
- **CPU 节点**：若真按 110 跑，`/26` 的 64 块只够 32 台。

要让节点数达到预期，两个方向：把该池节点的 `kubelet_max_pods` 调小（可按组配，方法同 [5.6](#56-gpu--cpu-用不同挂载目录)），或把 blockSize 调大（如 GPU 用 `/27` = 32 地址/块 → 256 块，每节点 ≤32 Pod 时成立）。

**节点怎么归池**：靠 `hardware=gpu` / `hardware=cpu` 节点标签（IPPool 的 `nodeSelector` 是 Calico selector 表达式 `hardware == "gpu"`，不是 k8s label 语法）。标签由 `kube-init-master` / `kube-add-node` / `kube-add-master` 下发，**仅在双池模式下才打**。判定依据是 inventory 行里的 `accelerator_type`：`nvidia`/`dcu`/`npu` → gpu 池，`none` 或没写 → cpu 池。

某台要覆盖自动判定，在它的 inventory 行加 `calico_pool=gpu` 或 `calico_pool=cpu` 即可（不用自己拼 `hardware=xxx` 那种键值对里套键值对的写法）：

```ini
[k8s_node]
10.0.0.11 ansible_host=10.0.0.11 accelerator_type=nvidia
10.0.0.12 ansible_host=10.0.0.12 accelerator_type=none calico_pool=gpu   # 强制进 GPU 池
```

> ✅ **网段规划由预检全量校验，不用再手工验算。** `roles/cni/tasks/calico.yaml` 开头两个任务（都是 `delegate_to: localhost` + `run_once`，纯配置校验、不碰目标机）：
>
> 1. **assert** —— 两个 `*_pool_cidr` 非空且形如 `a.b.c.d/n`（空着会渲染出 `cidr: ""` 的非法 IPPool，`apply` 未必报错但 Pod 永远拿不到 IP）；
> 2. **python3 预检** —— 逐项判：掩码取值是否合法（`/33` 会被拦）、`pod_subnet` 是否覆盖两个池段、两池之间是否重叠、三段是否与 `service_subnet` 重叠、v4/v6 是否混用；主机位非零（如 `10.244.0.0/12` → `10.240.0.0/12`）发警告但不拦。失败时把每一条问题都列出来，并提示 `pod_subnet` 建完集群不可改。
>
> 用的是 python3 标准库 `ipaddress`，**不依赖** `netaddr`/`ipaddr` 滤镜——控制节点必然有 python3（ansible 自己就要），所以 Kylin 离线环境也不用额外装包。
>
> 下面 [`pod_subnet` 超网怎么算](#pod_subnet-超网怎么算) 那段 python 片段仍然有用：规划阶段（还没写进 `env.yaml` 时）拿它试最小超网。

> ⚠️ **在已跑起来的集群上开启，光跑 `k8s-cni.yaml` 不够。** 打标签的任务只在 init / 加节点时执行，已有节点身上没有 `hardware` 标签。`NO_DEFAULT_POOLS=true` 之下，无标签节点两个池都匹配不上，按配置语义就拿不到可分配的地址块，新建 Pod 会卡在 sandbox 拿不到 IP。要在存量集群启用，先手工给全部节点补标签再 apply：
> ```bash
> kubectl label node <gpu节点> hardware=gpu --overwrite
> kubectl label node <cpu节点> hardware=cpu --overwrite
> kubectl get node -L hardware        # 确认每台都有值,再 apply
> ```
> 另外 Calico 的默认池一旦建成，改 `CALICO_IPV4POOL_CIDR` 是不生效的；存量集群从单池切双池，最干净的做法仍是 reset 重装。

> 封装模式两个池共用 `calico_encapsulation`（`none`/`ipip`/`crosssubnet`/`vxlan`），分别渲染成各池的 `ipipMode` / `vxlanMode`，不能按池分别设。

### 十三.2 升级 calico 版本：为新版本生成模板

⚠️ **只改 `calico_version` 是不够的。** `roles/cni/templates/calico/<版本>.yaml.j2` 是 7800+ 行 vendored 上游 manifest，只在 8 处做了参数化。改 tag 只换镜像版本，**上游新增的 CRD 与 ClusterRole 规则不会跟着变**。

> **模板按版本存放（2026-09-11 改）。** 原先是单一的 `templates/calico.yaml.j2`，配一条「模板版本必须等于 `calico_version`」的双向严格相等校验。那样**一份入库模板只能服务一个版本**，而 `calico_version` 在各站点自己的 `env.yaml`（gitignore）里 —— 后果是**所有站点必须同时换版本**：push 新模板的那一刻，落后的站点立刻撞 assert 装不了 CNI；想让老集群停在旧版也不行（双向相等，写旧版号照样被拦，没有退路）。
>
> 现在每个版本一个文件（`calico/3.31.3.yaml.j2`、`calico/3.32.2.yaml.j2` …），各站点按自己的节奏升级，**push 不再是同步点**。校验也从「版本相等」变成「该版本的模板存不存在」，缺了就明确告诉你去跑生成脚本。加新版本只写新文件，旧版本原样不动。

历史代价：3.27 → 3.31 那次只改了 tag，漏掉 9 个 CRD、2 条 ClusterRole 规则，症状是

```
felix: cannot list resource "clusternetworkpolicies" in API group "policy.networking.k8s.io" ... forbidden
felix: Connection to datastore has failed
→ CalculationGraph 永远 not ready → readiness 503 → calico-node 一直 NotReady → 整个集群没网络
```

而且残留到很久之后才被发现（`policy.networking.k8s.io` 那条只补了两个资源、漏了 `clusternetworkpolicies`；`kubevirt.io` 那条整条没有）。手工比对 7400 行不可靠，故脚本化。

#### 用法

```bash
# 1. 先看 diff, 不写入模板目录(产物落 calico-3.32.2.yaml.j2.new)
scripts/gen-calico-template.sh 3.32.2

# 2. 确认 diff 里的 CRD / ClusterRole 变化都合理, 再写入
#    新增版本 = 只写 templates/calico/3.32.2.yaml.j2, 其它版本原样不动;
#    重新生成同版本 = 覆盖并自动备份为 .bak-<时间戳>
scripts/gen-calico-template.sh 3.32.2 --apply

# 3. 改【本站点】env.yaml 的 calico_version, 并确认离线物料有该版本
#      calico_version: "3.32.2"
#    其它站点不用动 —— 它们的旧版模板还在, 各自按节奏升
ls offline/artifacts/cni/calico/v3.32.2/
```

diff 的基准：目标版本已存在就跟它自己比（重新生成同版本，正常应无差异）；不存在（新增版本）就跟**仓库里现有最高版本**比 —— 那才是「这次升级改了什么」的有效信息。一个版本都没有时跳过 diff。

离线环境拉不到上游时，先在有网机器上取文件，再用 `--from` 指定：

```bash
curl -O https://raw.githubusercontent.com/projectcalico/calico/v3.32.2/manifests/calico.yaml
scripts/gen-calico-template.sh 3.32.2 --from ./calico.yaml
```

#### 脚本做什么

| 步骤 | 内容 |
|---|---|
| 1 | 取上游 manifest（`curl` 或 `--from` 本地文件） |
| 2 | 施加参数化：3 处镜像、IPIP/VXLAN、`IP_AUTODETECTION_METHOD`、`NO_DEFAULT_POOLS`、bandwidth 段。**任一处未命中就报错退出**（说明上游结构变了，需人工核对正则，而不是生成一个缺参数化的模板）。bandwidth 是**条件必需**：上游自带时必须命中，上游没有则跳过（见下方） |
| 3 | 结构化 diff：按 `kind`+`name` 比对资源清单，**单独列出 CRD 增减、各 ClusterRole 的 rules 增减** |
| 4 | 校验：Jinja 能渲染 + 渲染后是合法 YAML + 参数化点都在 + 双池开关两种情形的 `NO_DEFAULT_POOLS` 计数正确 |

#### bandwidth 段：3.32.2 起上游删了

上游 3.28~3.31 在 CNI conflist 里默认写了 `bandwidth` 段，但 **calico-cni 镜像不含该插件二进制**（它属于 `containernetworking/plugins`）。裸着写进模板会让全节点 Pod 建不了 sandbox：

```
plugin type="bandwidth" failed (add): failed to find plugin "bandwidth" in path [/opt/cni/bin]
```

所以脚本把它包进 `{% if calico_enable_bandwidth %}`（默认 false）。**3.32.2 起上游自己删掉了这段**，那时无需包装，脚本打印 `SKIP(上游无此段)`。

> 历史 bug（2026-09-11 修，commit `93b7043`）：期望值曾写死成 1，于是 3.32.2 永远判"未命中"、`exit 3` 拒绝 `--apply` —— 站点的 `calico_version` 已是 3.32.2 却生成不出对应模板，彻底卡死。现在按上游是否自带该段决定期望 1 还是 0；**上游有但结构变了仍然照旧 exit 3**（不能放过，否则会把裸 bandwidth 段写进模板，后果比版本错配更重）。

副作用：3.32.2+ 生成的模板里没有 bandwidth 段，`calico_enable_bandwidth: true` **不再产生任何效果**（不报错，也不限速）。要在 3.32.2+ 上做 Pod 限速需另行往 conflist 加该段，脚本不做。

#### ⚠ diff 里带 `-` 和 ⚠ 的 ClusterRole 规则：先判断是不是误报

那表示「基准模板有、新生成的没有」。**但 verb 集合变化会同时产生一条 `-` 和一条 `+`**（脚本把规则拼成 `group/resource [verbs]` 字符串做集合差），所以**先在 `+` 行里找同名资源**：找到了就是上游改了 verbs，资源没丢，不用管。

3.31.3 → 3.32.2 实测三条 ⚠ 全都不用手工补：

| ⚠ 行 | 性质 |
|---|---|
| `kubevirt.io/virtualmachineinstancemigrations [list,watch]` | **误报** —— `+` 行里有 `[get,list,watch]`，上游收编了我们补的规则并多给了 `get` |
| `policy.networking.k8s.io/adminnetworkpolicies [list,watch]` | 上游删了 ANP CRD，**RBAC 和 CRD 一起删的**，自洽 |
| `policy.networking.k8s.io/baselineadminnetworkpolicies [list,watch]` | 同上（BANP） |

3.32.2 新增了 `clusternetworkpolicies` CRD，而它的授权**本来就在**（旧模板那条规则一次授了三个资源，diff 里没出现说明新旧都有），所以不会反过来出现"CRD 在但没权限"。

真正需要手工保留的判据：`-` 行的资源在 `+` 行里**找不到同名**，且上游确实没有。已知历史上补过两条：

```
policy.networking.k8s.io/clusternetworkpolicies
kubevirt.io/virtualmachineinstancemigrations
```

即便集群里没有这两个 CRD 也要授权：felix 无条件 watch 它们，没权限就报 forbidden 并判定 datastore 连接失败；而 CRD 不存在只会返回空列表，不影响。所以**不能因为"没装 KubeVirt"就不授权**。（3.32.2 起这两条上游都已自带。）

#### ⚠ 重新生成会冲掉手写注释

`gen-calico-template.sh` **不注入注释**。3.31.3 模板里那两段记录「`clusternetworkpolicies` 漏授权 → readiness 503」因果的手写中文说明，`--apply` 之后就没了（旧文件在 `.bak-*` 里还能捞）。手工加回下次跑脚本又会被冲掉 —— 要真正保留得改脚本让它注入，目前**未做**。

> 脚本自测方式（改动脚本后值得重跑）：把现有模板的 Jinja 还原成上游原值当作「伪上游」，再用脚本重新生成，结果应与现有模板**渲染等价**。实测：8 处参数化全命中、39 个资源集完全相同、`calico-node` ClusterRole 的 40 个资源逐条一致（含上面那两条）、双池开/关两种情形计数正确。

## 十三·五、运维附加(NodeLocal DNSCache / kubelet serving 证书)

两个独立 playbook,均可对**已跑起来的集群**重复执行(幂等),互不依赖。

### NodeLocal DNSCache(每节点本地 DNS 缓存)

降 CoreDNS 压力 / 省 conntrack。查询链:Pod(clusterDNS=`169.254.25.10`)→ nodelocaldns 本地缓存 → CoreDNS。
**忠实复刻现网 KubeKey/KubeSphere 版**:DS/CM/SA 名 `nodelocaldns`,单绑 `nodelocaldns_ip`,转发到运行时查到的
CoreDNS Service(`coredns`)ClusterIP。对现网 apply 是 **reconcile 同一 DS(幂等,不新建)**。

**推荐:随装机自动部署**(与 kk 同款做法)。在 env.yaml 置 `enable_nodelocaldns: true` 后,
`k8s-install.yaml` / `k8s-init-master.yaml` 会在 **CNI 之后**自动部署 DaemonSet,并让 kubeadm 把
kubelet 的 `clusterDNS` 指向 `nodelocaldns_ip`;worker 由 `kubeadm join` 拉 `kubelet-config`
ConfigMap 自动继承,无需单独配。

```yaml
# env.yaml
enable_nodelocaldns: true
```

> 为什么 kubeadm init 阶段就能把 DNS 指向"还没部署"的地址?
> 因为 nodelocaldns 与 coredns 都是 `hostNetwork: true` + `dnsPolicy: Default`,走宿主机 DNS 启动,
> 不依赖集群内解析;真正需要集群 DNS 的业务 Pod 起来时它早已就绪。

**事后单独部署/重配**(已跑起来的集群,或没开上面那个开关时):

```bash
ansible-playbook -i inventory/hosts playbook/nodelocaldns.yaml                    # 在线
ansible-playbook -i inventory/hosts playbook/nodelocaldns.yaml -e is_offline=true # 离线(需先备镜像)
# 验证
kubectl -n kube-system get ds nodelocaldns            # DESIRED==READY(全节点)
ip addr show nodelocaldns                             # 有 169.254.25.10
kubectl exec <任意业务Pod> -- cat /etc/resolv.conf     # nameserver 应为 169.254.25.10
```

> ⚠ 单独跑本 playbook 时,若 kubelet 的 `clusterDNS` 仍指向 coredns ClusterIP,
> Pod **不会**走本地缓存 —— 装了等于白装。要么用上面的开关随装机做,要么手工改各节点
> `/var/lib/kubelet/config.yaml` 的 `clusterDNS` 并重启 kubelet。
>
> ⚠ 已在运行的 Pod 不会自动更新 `/etc/resolv.conf`,需重建才生效。

**kube-proxy 模式**:本模板是**单绑**(只绑 link-local,不拦截 ClusterIP)形态,
`iptables` / `ipvs` 两种模式都适用。只有官方**双绑**版(同时绑 kube-dns ClusterIP)才依赖
iptables NOTRACK、与 ipvs 冲突。

**变量(默认放 defaults.yaml,站点专属放 gitignored env.yaml):**

| 变量 | 默认 | 说明 |
|---|---|---|
| `enable_nodelocaldns` | `false` | **置 true 则随装机自动部署**并自动设 kubelet `clusterDNS`;不开则需单独跑 playbook |
| `nodelocaldns_ip` | `169.254.25.10` | 必须与各节点 kubelet `clusterDNS` 一致(现网即此值) |
| `nodelocaldns_version` | `1.26.4` | `registry.k8s.io/dns` 正规上游 tag(现网即此);换版本在 env.yaml 覆盖 |
| `nodelocaldns_image_online` | `k8s.m.daocloud.io/dns/k8s-dns-node-cache` | 在线源(= `registry.k8s.io/dns/...`,daocloud 国内加速) |
| `nodelocaldns_coredns_svc` | `coredns` | 上游 CoreDNS svc 名(kubeadm 原生叫 `kube-dns`) |
| `nodelocaldns_stub_zones` | `[]` | **站点专属→env.yaml**;每项 `{zone, forward, cache(可选30), health(可选)}` |
| `nodelocaldns_hosts` | `[]` | **站点专属→env.yaml**;`.:53` 静态解析,每项 `{ip, names:[...]}` |

env.yaml 示例(现网那两段站点定制):
```yaml
nodelocaldns_stub_zones:
  - { zone: "e2-s3.msh.team", forward: "10.200.82.49", cache: 10 }
nodelocaldns_hosts:
  - { ip: "10.82.254.130",  names: ["moonshot-registry-vpc.cn-beijing.cr.aliyuncs.com"] }
  - { ip: "10.92.33.8",     names: ["msh-m2-registry-vpc.ap-southeast-1.cr.aliyuncs.com"] }
  - { ip: "172.24.111.254", names: ["msai-cn-beijing.cr.volces.com"] }
```

> ⚠️ `nodelocaldns_ip` **必须与各节点 kubelet `clusterDNS` 一致**;不一致 Pod 会把 DNS 发往未监听 IP → 全部解析失败。
> ⚠️ 现网已在运行(名字/结构一致),apply 前先确认渲染出的 manifest 与现网一致再动生产。
> **`--check` 可以当预览用**（只读任务已带 `check_mode: false`，机理同 [5.4](#54-实跑前的预览与盘点)）：
> ```bash
> ansible-playbook -i inventory/hosts playbook/nodelocaldns.yaml --check --diff
> ```
> 会探测上游 CoreDNS svc、渲染 manifest 并用 `--diff` 打出内容差异，然后跳过 `apply` 与 `rollout`；离线时也跳过镜像 load/push。
>
> ⚠️ check 模式下 `template` **不落盘**，所以此时磁盘上没有新文件，`kubectl diff` 读到的是上次实跑留下的旧文件（或报文件不存在）。想拿 `kubectl diff` 比对**本次渲染结果**与现网，走单步跑：
> ```bash
> # ① 先备份现网对象(真正的兜底, 出问题能还原)
> kubectl -n kube-system get ds,cm,sa nodelocaldns -o yaml > /root/nodelocaldns-backup.yaml
> # ② 单步跑, 停在 "apply nodelocaldns" 之前, 另开终端比对
> ansible-playbook -i inventory/hosts playbook/nodelocaldns.yaml --step
> kubectl diff -f /etc/kubernetes/nodelocaldns.yaml     # 无输出=完全一致
> ```
> 或先在测试集群验一遍。
> 前提:kube-proxy 为 **iptables** 模式(role 内已 assert)。
> 离线镜像 `k8s-dns-node-cache` 由 `download-k8s-offline.sh` 从 `k8s.m.daocloud.io/dns`(= `registry.k8s.io/dns` 上游,daocloud 加速)拉,与组件镜像一起放 `.../kubernetes/v{k8s}/images/`。

### kubelet serving 证书(serverTLSBootstrap + 审批 kubelet-serving CSR)

现网 kubelet 10250 是自签名证书,`metrics-server`/`kubectl top`/`exec`/`logs` 需 `--kubelet-insecure-tls`。
开 `serverTLSBootstrap` 后 kubelet 向集群 CA 申请正规 serving 证书,再审批 `kubernetes.io/kubelet-serving` CSR。
新集群 kubeadm 模板已自带 `serverTLSBootstrap: true`,**本 playbook 仅用于存量集群补下发**。

```bash
ansible-playbook -i inventory/hosts playbook/kubelet-serving-cert.yaml   # 全节点(master+worker)
# 验证
kubectl get csr | grep kubelet-serving                                   # Approved,Issued
openssl s_client -connect 127.0.0.1:10250 </dev/null 2>/dev/null | openssl x509 -noout -issuer -ext subjectAltName
```

> 全节点幂等下发(`lineinfile` 替 sed);顺带 patch `kubelet-config` ConfigMap → 新节点 join / kubeadm upgrade 不丢;
> CSR 自动审批**只批 signer=kubelet-serving 且请求者是已知 inventory 节点**,不误批。
> 证书到期(kube-controller-manager `--cluster-signing-duration`,默认 1y)重签会再产 CSR,重跑本 playbook 即可。

## 十四、多版本 K8s 与国内镜像

**多版本**：`k8s_version` 是唯一真源（同 `containerd_version` 思路），改一处即切换。版本变量分三类：

- **A 组（跟 k8s 版本走，基本不用管）**：`coredns` / `pause` / `crictl`。装 k8s 时 playbook 会**自动跑 `kubeadm config images list --kubernetes-version v{{ k8s_version }}` 拿权威值**覆盖，不用手查。`k8s_compat` 矩阵只做两件事：① containerd 的 sandbox(pause) 镜像（k8s 装之前就要用，来不及查）；② 查不到时的兜底默认。当前列了 **1.28 / 1.34 / 1.35 / 1.36** 四支；起新版本装时会自动查，若 pause 变号再加一行。
- **B 组（独立选，跟 k8s 无关）**：`calico` / `flannel` / `cilium` / `helm`——这些按各自的 k8s 兼容矩阵挑，不从 k8s 版本推。
- **`etcd`（跟 k8s 版本走，但三处各自取值）**：它**不在 B 组**——`k8s_compat` 表里有 etcd 列，`defaults.yaml` 的 `etcd_version` 就是按 `k8s_minor` 派生的。详见下条。

> 换 k8s 版本正常只改 `k8s_version` 一处即可；A 组自动对齐（在线 kubeadm 自己选，离线由上面的自动查询对齐 tar）。

> **etcd 的三处取值口径**（权威说明在 `defaults.yaml` 的 `etcd_version` 那段注释）：
> - **下载端**：`download-k8s-offline.sh` 跑 `kubeadm config images list` 校准（权威值，`3.6.8-0 → 3.6.8`），按 `v<版本>/` 建目录；
> - **离线部署**：`roles/etcd/etcd-install` **直接扫 `offline/artifacts/etcd/` 取实际下到的版本**，既不看 env.yaml 也不看 `k8s_compat`（多个版本取最新；目录为空则明确报错而非拼出不存在的路径）。所以离线场景下在 env.yaml 手写 `etcd_version` **完全无效**；
> - **在线部署**：用 `k8s_compat` 的派生值。
>
> ⚠ `k8s_compat` 的 etcd 列**是兜底、会随 k8s 补丁版飘**（如 1.34.3 实际是 3.6.5 而非 3.6.4），以 kubeadm / 物料为准。所以**正常不要在 env.yaml 手写 `etcd_version`**。
>
> 真要钉死（外置 etcd 独立运维、故意跑比 kubeadm 推荐更新的补丁版）才写它。写了之后装控制面时（`kubeadm config images list` 已可跑）会拿 kubeadm 推荐的 etcd tag（剥 `-N` 后缀）与 `etcd_version` 比对：一致打 ✓，漂移打 ⚠（默认只告警不拦）。想让漂移直接失败，env.yaml 设 `etcd_version_strict: true`。

- 离线包按版本分目录：`offline/artifacts/kubernetes/v{{ k8s_version }}/{bin,images}/{amd64,arm64}/`；想并存多版本就放多个 `v1.32.10/`、`v1.34.3/`，切版本只改变量。
- 在线二进制从 `k8s_bin_mirrors` 里的源逐个尝试：`<源>/v{{ k8s_version }}/bin/linux/{arch}/`。

### 升级 k8s 版本 checklist（示例 1.34.3 → 1.36.x）

**① 改一处（唯一真源）**：env.yaml `k8s_version: "1.36.x"`。用**真实 patch 号**——先 `curl https://dl.k8s.io/release/stable-1.36.txt` 查，否则 kubeadm 二进制 404。

**② 自动跟上、不用管**：
- `k8s_minor` → `1.36`，`k8s_compat` 已有该行 → pause/coredns/crictl 都有值，不会 undefined（新起的版本若表里没有，加一行或靠 kubeadm 自动查）。
- 装 k8s 时 kubeadm 1.36 `config images list` 拿 coredns/pause 权威值覆盖（在线自选；离线由 `download-k8s-offline.sh` section 1.5 用 kubeadm 1.36 校准 tar）。
- 两个附加特性（kubelet serving 证书 / nodelocaldns）与版本无关，照跑。

**③ 重下离线物料**（离线场景）：
```bash
ansible-playbook playbook/gen-offline-versions.yaml   # 刷 versions.env(CRICTL 等随之变)
bash scripts/offline/download-k8s-offline.sh          # 拉 v1.36.x 的 bin+images
```
物料按 `v{{ k8s_version }}/` 分目录，v1.34.3 保留、v1.36.x 并存，切版本只靠变量。

**④ etcd 会命中一致性校验**：`etcd_version` 手钉不变；装控制面时若与 kubeadm 1.36 推荐的 etcd tag 不一致会打 ⚠（默认不拦），据此判断要不要 bump 外置 etcd。

**⑤ 需**手工**确认的兼容性（仓库替你查不了）**：

| 项 | 为什么要查 |
|---|---|
| **containerd / runc 版本** | 新 k8s 对 CRI/containerd 有最低版本要求；看 1.36 release notes，可能要升 `containerd_version`（`runc_version` 随之）。这俩跟 `k8s_version` 无自动联动。 |
| **CNI（calico/cilium/flannel）** | B 组，按各自对 1.36 的兼容矩阵挑，新 k8s 常要 bump，改 env.yaml 对应版本。 |
| **crictl** | `k8s_compat` 里的 crictl（如 1.36.0）要确认 cri-tools 有对应 release。 |

> 一句话：**k8s 自己那套（A 组 + kubeadm 自动）改 `k8s_version` 一处即可**；真正要动脑的是 kubeadm 管不着的**底座（containerd/runc）和 CNI**，外加看一眼 etcd 校验的 ⚠。

**官网受限 → 国内镜像**（全部变量化，默认已指国内，可随意改）：

| 变量 | 默认 | 用途 |
|---|---|---|
| `kube_image_repository` | 离线自建 Harbor / 在线 `registry.aliyuncs.com/google_containers` | kubeadm 组件镜像（`is_offline` 自动切） |
| `kube_image_mirror` | `registry.aliyuncs.com/google_containers` | 在线组件镜像 mirror |
| `calico_registry_online` / `flannel_registry_online` / `cilium_registry_online` | docker.io/calico、docker.io/flannel、quay.io/cilium | 在线 CNI 镜像仓（受限可换国内 mirror） |
| `k8s_bin_mirrors` | `[files.m.daocloud.io/dl.k8s.io/release, dl.k8s.io/release]` | 在线下载 kubeadm/kubectl/kubelet。**复数=列表**，多源失败自动切换；覆盖时要给完整列表 |

## 十五、扩缩容与卸载（节点 / etcd / 底座）

> **加节点：只「加」新节点到清单，别注释老的**。inventory 里 `[cluster]`/`[containerd]`/`[k8s_node]`(或 `[k8s_master]`) 各加一行新节点即可；要挂盘的还要按盘的形态加进 `[nvme_single]` 或 `[nvme_lvm]`（见 [5.6](#56-gpu--cpu-用不同挂载目录)）。示例（新增 cpu220 worker，单盘）：
> ```bash
> ansible-playbook playbook/init.yaml             --limit cpu220   # ★ 必须 --limit
> #   纯在线环境不想碰离线源配置: 加 --skip-tags repo(只跳过装离线 apt 源那两个任务,
> #   其余初始化正常跑); 配合 -e is_offline=false 一起用
> ansible-playbook playbook/mount-nvme.yaml       --limit cpu220   # 按需; hosts 已是 nvme_single, --limit 再收窄一层
> ansible-playbook playbook/containerd-setup.yaml --limit cpu220   # ★ 必须 --limit
> ansible-playbook playbook/harbor-trust.yaml      --limit cpu220   # 按需; hosts 是 docker:containerd 并集
> ansible-playbook playbook/k8s-add-node.yaml                      # 可不加(见下)
> ansible-playbook playbook/kubelet-serving-cert.yaml              # 见下方说明, 别漏
> ```
> **`kubelet-serving-cert.yaml` 这一步容易漏**：存量集群若已开 `serverTLSBootstrap`，新节点 join 后会产生一条 `kubernetes.io/kubelet-serving` CSR，没人批的话 10250 端口没有可用证书，表现为 `kubectl logs`/`exec` 报 `tls: internal error`（新节点独有，老节点不受影响）。老节点会自动跳过，只处理新节点 CSR，重跑安全。跑完用这条验证证书确实由集群 CA 签发（不是自签名）：
> ```bash
> ansible k8s_node -b -m shell -a "echo | openssl s_client -connect 127.0.0.1:10250 2>/dev/null | openssl x509 -noout -issuer -dates 2>/dev/null"
> ```
> **`--limit` 什么时候必须**：
> - **`init` / `os-init` / `containerd-setup`（底座）→ 必须 `--limit 新节点`**。它们作用于
>   `cluster`/`containerd`/`init` 组且**没有早停保护**，不限制会在老节点重跑并重启服务：
>   `containerd-setup` 重启 containerd（**扰动运行中的 Pod**，影响最大）；
>   `init` 重启 chrony / systemd-resolved；`os-init` 重启 CPU governor 服务（`os-cpu-performance.service`）。
>   后两者影响较小，但既然没有早停就都该 `--limit`。
> - **挂盘三个 playbook → 建议加但不再是唯一防线**。它们的 `hosts` 已改成 `nvme_single` / `nvme_lvm`
>   （不是 `cluster`），只作用于你显式放进组的机器，组留空则直接跳过。老节点已挂好的会走幂等分支
>   （`mount-nvme` 跳过格式化、LVM 那两个跳过选盘清盘），但加 `--limit` 更省事也更明确。
>   ⚠ **三个怎么选看的是盘的形态，不是节点是不是 GPU**：单盘进 `[nvme_single]` 跑 `mount-nvme.yaml`；
>   2/4 块盘做 LVM 进 `[nvme_lvm]` 跑 `mount-nvme-lvm.yaml`；4 块 3.5T 交付标准场景改用
>   `mount-nvme-lvm-containerfs.yaml`（**会清盘**，见 [五、数据盘挂载](#五数据盘挂载)）。
>   现网 GPU 节点常年多盘、CPU 节点常年单盘，容易让人以为是按角色选，其实是按 inventory
>   分组走的——同一台机器盘形态变了，组也要跟着改，不是看它是 `gn-` 还是 `cn-`。
> - **`k8s-add-node` / `k8s-add-master` / `k8s-install`（k8s 层）→ 可不加**。三者都在 `pre_tasks` 里做
>   「已加入判定」并 `meta: end_host` 整台早停，在网节点连 `kube-common` 都不会跑，全跑也安全
>   （`--limit` 只是更快）。判定为双重判据：先到 first master `kubectl get node <本机名>`，
>   kubectl 不可用时回退看本机 `kubelet.conf`（防 API 抖动把在网节点误判为未加入）。
>   需要对**已加入**节点重下发配置时加 `-e force_common=true`（此时仍拦住 join，即"只重配置、不重加入"）。
>   ⚠ 早停必须在 `kube-common` 之**前**：`kube-common` 的 `deploy-config` 改动 kubelet unit /
>   drop-in 时会 `notify` 重启 kubelet，对在网 master 就是控制面逐台抖动 —— 并非"幂等无重启"。
> - 加 master 同理：新节点进 `[k8s_master]`，`k8s-add-master.yaml`(可选 `--limit`)。加多台 `--limit 'cpu220,cpu221'`。

### CPU / GPU 加节点完整流程（现网实操整理）

上面是单个 playbook 该不该带 `--limit` 的原则；下面是从零到验证通过的完整链路，区分 CPU / GPU 两条真实路径。

**通用前置（一次性，两条路径都要）**：

```bash
# 1. 全节点 /etc/hosts 互写(k8s_master + k8s_node 去重合并)——与 cp-endpoint-hosts.yaml 是两件事,
#    后者只写 controlPlaneEndpoint 域名解析
ansible-playbook playbook/host-set.yaml

# 2. 控制机免密下发到本次要初始化的节点(先用 auto, 自动探测走 root 还是 sudo)
ansible-playbook playbook/add-control-key.yaml -e target_hosts=init -e connect_as=auto

# 3. 需要走代理装包时才要。apt-proxy 只对 [init] 组生效, 与节点是不是 GPU 无关
#    (不用 all 的原因见 apt-proxy.yaml 头部注释: [harbor]/[chronyserver] 常写裸 IP,
#     会被当成独立主机重复处理)
ansible-playbook playbook/apt-proxy.yaml
```

**CPU 节点**：

```bash
ansible-playbook playbook/init.yaml -e init_config_dns=true -e is_offline=false
ansible-playbook playbook/mount-nvme.yaml -e device_path=/dev/nvme0n1   # 单盘; 多盘按上面的挂盘说明换 playbook
ansible-playbook playbook/containerd-setup.yaml
ansible-playbook playbook/harbor-trust.yaml
ansible-playbook playbook/k8s-add-node.yaml
ansible-playbook playbook/kubelet-serving-cert.yaml
```

**GPU 节点**：

```bash
ansible-playbook playbook/init.yaml -e is_offline=false   # 不传 init_config_dns, 沿用默认 false
ansible-playbook playbook/mount-nvme-lvm-containerfs.yaml  # 自动识别多盘; 非 4 块 3.5T 交付标准场景换 mount-nvme-lvm.yaml
ansible-playbook playbook/containerd-setup.yaml
ansible-playbook playbook/harbor-trust.yaml
ansible-playbook playbook/k8s-add-node.yaml
ansible-playbook playbook/kubelet-serving-cert.yaml
```

> ⚠ 两条路径的差异只在 `init_config_dns` 传不传、挂盘选哪个 playbook——这些是站点的刻意区分，
> 不是"CPU 就该怎样、GPU 就该怎样"的固定规则，实际选哪个仍取决于该节点的 DNS 需求和盘的形态。

**验证**：

```bash
# 证书确认是集群 CA 签发, 不是自签名(全量或按需 -l 收窄, 如只验一批新节点)
ansible k8s_node -b -m shell -a "echo | openssl s_client -connect 127.0.0.1:10250 2>/dev/null | openssl x509 -noout -issuer -dates 2>/dev/null"

# 参数生效核对: 全部由上面 init.yaml 那步静态写入 sysctl.conf / systemd, 这里只是验证不是配置
ansible init -m shell -a 'for p in net.core.somaxconn net.core.netdev_max_backlog net.core.rmem_max net.core.wmem_max fs.file-max user.max_user_namespaces net.ipv4.ip_local_port_range kernel.keys.maxkeys kernel.keys.maxbytes; do printf "%-30s %s\n" "$p" "$(sysctl -n $p)"; done'
ansible init -m shell -a "systemctl show --property DefaultTasksMax"   # 应为 infinity, 见下方 ⚠

# k8s 层业务标签(仓库不识别, 纯按主机名前缀自定义打的, 与 inventory 的 accelerator_type 无耦合)
kubectl label no $(kubectl get no | grep gn | awk '{print $1}') nvidia=true
kubectl label no $(kubectl get no | grep cn | awk '{print $1}') cpu_node=true
```

> ⚠ **不需要手动 `sed` 改 `DefaultTasksMax`**——`init.yaml` 默认就会把它设成 `infinity`
> （见 [四、系统初始化](#四系统初始化inityaml在线离线同一入口) 与十七排查表），上面已经跑过了。
> 手动补一刀不会报错，但也不会有实际效果，见下方排查表那一行的坑。

```bash
# ---- worker ----
ansible-playbook playbook/k8s-add-node.yaml                     # 加(填 [k8s_node] 新节点)
ansible-playbook playbook/k8s-del-node.yaml                     # 删(填 [node_to_delete])

# ---- master ----
ansible-playbook playbook/k8s-add-master.yaml                   # 加(新节点直接进 [k8s_master], 已加入的自动早停)
# ⚠ 不要填 [master_to_add] —— 该 playbook 的 hosts 是 k8s_master, 填到 master_to_add 里
#   的节点【不会被操作】。master_to_add 只给 LB 扩容用(lb-scale / lb-nginx-install 读它,
#   目的是把"即将成为 master"的节点提前加进 haproxy/nginx 后端)。

# ---- etcd ----
ansible-playbook playbook/etcd-scale-up.yaml                     # 扩(填 [etcd_to_add])
ansible-playbook playbook/etcd-scale-down.yaml                   # 缩(填 [etcd_to_delete],保护:剩余<2 中止)
ansible-playbook playbook/etcd-config-update.yaml               # 同步 etcd 配置
ansible-playbook playbook/etcd-destroy.yaml                      # 销毁 etcd(慎用)

# ---- 整集群重置(重装前清场) ----
ansible-playbook playbook/k8s-reset.yaml -e confirm_reset=yes   # 所有 master+worker kubeadm reset+清理
#   默认同时清空外置 etcd 数据(否则重装会撞旧数据); 想保留 etcd 数据加 -e reset_etcd=false
```

> `k8s-reset.yaml` 是破坏性操作，**必须加 `-e confirm_reset=yes`** 才执行。它对 `[k8s_master]`+`[k8s_node]` 跑 `kubeadm reset` + 清目录/CNI 网卡/iptables，并默认销毁 `[etcd]`（用 `etcd-destroy`;外置 etcd `kubeadm reset` 不会清,不清则重装会撞旧数据）。清完即可重新 `k8s-install`。

### 底座卸载

| 组件 | playbook | 目标组 | 默认行为 |
|---|---|---|---|
| containerd | `containerd-remove.yaml` | `[containerd]` | 只删二进制 + service 文件，**保留** `/etc/containerd` 与数据目录（避免误删镜像） |
| docker | `docker-remove.yaml` | `[docker]` | 只删本 role 装在 `/usr/local/bin` 的那份；包管理器装的 docker-ce **不动** |
| harbor | `harbor-remove.yaml` | `[harbor]` | `docker-compose down` + 删镜像 + **直接删除** `harbor_copy_path`/`data_volume` 整个目录 |

```bash
# ---- containerd ----
ansible-playbook playbook/containerd-remove.yaml --limit <节点>                               # 保留配置/数据
ansible-playbook playbook/containerd-remove.yaml --limit <节点> -e purge_containerd_data=true # 彻底清(删 /etc/containerd 与数据目录)

# ---- docker(仅给 Harbor 用的那份;k8s 节点跑 containerd,不受影响) ----
ansible-playbook playbook/docker-remove.yaml --limit <节点>

# ---- harbor(⚠ 无二次确认参数,直接删数据) ----
ansible-playbook playbook/harbor-remove.yaml
```

> ⚠️ **`docker-remove.yaml` 会自动避开复用中的 containerd**：探到本机 `/usr/local/bin/containerd` 存在（k8s 节点复用的那套）就跳过它和 `runc`/`ctr`/`containerd-shim-runc-v2`/`containerd.service`，只卸 docker 自身；原理与历史踩坑见 [十七 · 挂盘/Docker/containerd](#挂盘--docker--containerd) 的「卸 docker 之后 containerd 也挂了」那一行。卸载完成后终端会打印这次的排除范围，确认一下再继续。
>
> ⚠️ **`harbor-remove.yaml` 没有 `purge_data` 这类开关**，跑起来就是直接删 `docker-compose down` + 镜像 + `harbor_copy_path`（Harbor 安装目录）+ `data_volume`（Harbor 数据目录，默认镜像仓库全部内容），执行前确认这台是不是还有别的集群在用这个 Harbor。

其它 LB 卸载：`lb-nginx-remove.yaml` / `lb-haproxy-remove.yaml`（对应装的时候选的是 nginx-ha 还是 haproxy-ha）。

## 十六、离线部署（完整流程）

无外网环境部署。核心：**`is_offline=true` 全链路 + 物料提前打包 + 镜像走自建 Harbor 中转**。

### 1. 联网机打包物料

在**有网 + 有 docker** 的机器上（可与内网不同架构，脚本拉双架构）：

> ⚠ **`ansible` 这一层必须先跑，且是两步、不是一步**：这里的 `download-ansible-offline.sh` 只是
> **下载**——产物落 `offline/ansible-pkg-install/`，此时内网机器仍然**没有** ansible。要把这个目录
> 拷进内网、在**内网控制机**上跑 `bash scripts/install_ansible.sh` 才是真正的**安装**（下方有说明）。
> 装完 `ansible --version` 能跑通，才能开始执行本项目剩下的全部 `ansible-playbook` 命令——顺序反了
> （比如先把其余几层下完才想起 ansible）也不影响物料本身，但控制机走不到能跑 playbook 的那一步。

```bash
# ansible 自身离线包(内网机器没装 ansible 时先做; 取各系统当前最新版, 双架构)
bash scripts/offline/download-ansible-offline.sh        # 或指定 kylin / ubuntu / openeuler
# OS 基础包(按发行版)
bash scripts/offline/download_ubuntu_packages.sh      # 或 kylin / openeuler
# k8s 层物料(k8s二进制/组件镜像/etcd/CNI镜像/helm+cilium chart, 双架构)
bash scripts/offline/download-k8s-offline.sh
# 底座运行时 + docker 层(containerd/runc + docker静态包 + buildx + compose + cri-dockerd, 双架构)
bash scripts/offline/download-docker-offline.sh
# NVIDIA GPU(nvidia-container-toolkit rpm+deb; DCU/NPU 厂商私有需手动放包)
bash scripts/offline/download-gpu-offline.sh            # 仅 amd64(GPU 节点基本都是 x86)
# harbor 物料(12 个 goharbor 组件镜像 + docker-compose, 仅 amd64)
bash scripts/offline/download-harbor-offline.sh
```

> **一键预取(推荐)**：上面各层可由 `scripts/prefetch-all.sh` 统一编排，架构/发行版**在 env.yaml 声明一次**(学 kk)，不用每次手打 `ARCH=`/`DISTRO=`：
> ```yaml
> # inventory/group_vars/all/env.yaml
> offline_arch: amd64                 # amd64 | arm64 | all(不填=all=双架构)
> offline_distros: [ubuntu, kylin]    # all 或列表; 只对 packages 层生效, 用不到的发行版不下
> ```
> ```bash
> bash scripts/prefetch-all.sh k8s docker harbor gpu packages   # 范围自动读 env.yaml
> ```
> - **优先级**(高覆低)：环境变量 `ARCH=`/`DISTRO=` > env.yaml(`offline_arch`/`offline_distros`) > `all`。临时想只下别的，命令行前缀 `DISTRO=ubuntu`/`ARCH=amd64` 即可临时压过 env.yaml。
> - **下载失败不再静默**：某发行版/架构下崩(如麒麟容器解析不到官方源 `update.cs2c.com.cn`)会在**末尾红字汇总并非零退出**，不会「直接下一步」让你以为下完了。麒麟这类多是**联网机容器 DNS/路由**问题(非脚本 bug)——可重试、或 `DOCKER_DNS=223.5.5.5 bash scripts/prefetch-all.sh packages` 指定稳定 DNS、或在 `offline_distros` 里剔除拉不到的发行版。
> - **镜像只拉一次**：各 packages builder 首次按架构拉基础镜像后打本地缓存标签(`pkgcache/*`)，之后复用不再重复拉双架构(docker 同一 tag 本地只能存一个平台,否则双架构会互相顶掉、每次重拉)。

> **单架构集群省一半体积/时间**：以上 `download-ansible-offline.sh` / `download-k8s-offline.sh` / `download-docker-offline.sh` 均默认双架构(`all`)，可加架构参数只下一份 —— 纯 x86 集群用 `amd64`、纯 arm 集群用 `arm64`。(走 `prefetch-all.sh` 则由 env.yaml 的 `offline_arch` 统一控制,见上。)
> ```bash
> bash scripts/offline/download-k8s-offline.sh amd64
> bash scripts/offline/download-docker-offline.sh amd64
> bash scripts/offline/download-ansible-offline.sh all amd64   # 第1参=发行版, 第2参=架构
> ```
> 大头在 k8s 组件/CNI 镜像(每镜像每架构各存一份 `.tar.gz`)，单架构基本减半。混合架构集群(x86 master + arm worker)或以后要加异构节点，保持默认 `all`。GPU 脚本只出 amd64(GPU 节点基本都是 x86;arm64+N 卡如 GH200/Jetson 属少数平台，本项目不覆盖)。
>
> **单架构只需命令行加参数，不用改任何配置/变量**：
> - 参数填的是**目标集群机器**的架构，不是下载机的架构 —— 纯 arm 集群哪怕在 x86 机上下也填 `arm64`(脚本用 skopeo `--override-arch` / docker `--platform` 精确拉，不看下载机)。
> - **部署侧(ansible)无需任何架构配置**：roles 靠 `ansible_architecture` 自动判架构选对应文件，你下了哪份就自动对上。
> - 结论:**双架构=默认什么都不做；单架构才需要多打一个 `amd64`/`arm64`**。只在确定集群纯单架构时才加。

`download-ansible-offline.sh` 调用 `download_{kylin,openeuler,ubuntu}_ansible.sh`(容器内 `yum install --downloadonly` / `apt install --download-only`,只抓 **ansible + 目标机缺失的依赖**,不再拉整棵依赖树),产物 `offline/ansible-pkg-install/ansible_<系统><版本>_<arch>.tar.gz`。

内网机器装 ansible **直接跑 `bash scripts/install_ansible.sh`**——它自动识别本机**系统**(kylin/openEuler/ubuntu,ubuntu 再分 22/24)与**架构**(x86_64/arm64),选对应 tar 离线安装(RHEL 系 `yum localinstall`、Debian 系 `dpkg -i`),兼容带顶层目录/平铺两种打包,装完校验 `ansible --version`。默认会在 `scripts/ansible-pkg-install`、仓库 `offline/ansible-pkg-install` 里找包;都不在时指定目录:`bash scripts/install_ansible.sh <离线包目录>`。手动装则解压后 `cd` 进目录 `rpm -Uvh --force ./*.rpm`(RHEL 系) 或 `dpkg -i ./*.deb`(Debian 系,跑两遍解顺序)。

> ✅ 到这里 `ansible --version` 能跑通，控制机才算真正就位——上面 §1 开头提的两步（下载→安装）完成。
> 后续的 `init.yaml`/`k8s-install.yaml` 等 `ansible-playbook` 命令都要从这台机器上跑。

`download-k8s-offline.sh` 特性：源走 **daocloud**（`files.m.daocloud.io`，国内快）；**双架构**（amd64/arm64）；pull 重试 + **断点续传**（已下好的跳过）；下载**大小校验**、镜像 tar 完整性校验，残缺自动重下。顶部变量可改版本/裁剪 `CNIS`。

> ⚠️ `coredns`/`pause` 版本脚本里写死，换 k8s 版本前用 `kubeadm config images list --kubernetes-version vX.Y.Z` 核对改顶部变量。

`download-harbor-offline.sh` 用 skopeo 按 amd64 拉 12 个 goharbor 组件镜像(v2.11.2)存成 `harbor/x86/<组件>-v2.11.2.tar.gz`(对齐 `harbor_offline_images`)+ `docker-compose.x86`。**仅 amd64**：goharbor 官方无任何版本的 arm64 镜像([多架构 PR 仍 stalled](https://github.com/goharbor/harbor/pull/21825))。arm64(`harbor_images_aarch64`,v2.13.0)来自 [octohelm/harbor](https://github.com/octohelm/harbor) 的现成多架构镜像(`ghcr.io/octohelm/harbor/<组件>:v2.13.0`,国内可走 `ghcr.m.daocloud.io`),复用已做好的那批 tar 即可,本脚本不代下。

打包完把整个仓库（含 `offline/artifacts/`）拷进内网。物料目录结构见 [九](#九离线二进制目录结构)。

### 2. 打开离线开关

`inventory/hosts` 的 `[all:vars]` 设一次（全链路生效，免每条 `-e`）：
```ini
[all:vars]
is_offline=true
```
效果：OS 包走本地 repo；`sandbox_image`/`kube_image_repository` 指自建 Harbor；CNI 镜像本地 tar 推 Harbor；二进制全来自离线包（在线下载 mirror 变量不生效）。

### 3. 部署顺序（离线）

```bash
bash init.sh                                    # 生成 inventory/hosts + env.yaml,填好
ansible-playbook playbook/add-control-key.yaml  # (可选)控制机→各节点免密(首次加 -k)
ansible-playbook playbook/init.yaml             # env.yaml 置 is_offline=true -> 走离线包
ansible-playbook playbook/mount-nvme.yaml        # 按需
ansible-playbook playbook/containerd-setup.yaml # sandbox=Harbor
ansible-playbook playbook/docker-install.yaml
ansible-playbook playbook/harbor-install.yaml   # ★ Harbor 必须先起(离线镜像中转站)
ansible-playbook playbook/harbor-trust.yaml
ansible-playbook playbook/etcd-deploy.yaml
ansible-playbook playbook/k8s-install.yaml      # 载入 k8s/CNI 镜像->推 Harbor->kubeadm init
ansible-playbook playbook/k8s-add-node.yaml
```

### 4. 关键点 / 坑

- **`is_offline` 全链路一致**：要么 `[all:vars]` 设一次，要么每条都 `-e is_offline=true`，**别混**（在线装的 containerd sandbox=aliyun，再离线跑 k8s 会对不上）。
- **Harbor 必须在 k8s-install 之前就绪**——离线时 k8s 组件/CNI/pause 镜像全从本地 tar `docker load` 后推 Harbor，kubeadm/CNI 再从 Harbor 拉。顺序：containerd → docker → **harbor** → etcd → k8s。
- **镜像 tar 命名**要和 sync 期望对齐（打包脚本已对齐，自己加镜像时注意）。
- **CNI 选谁备谁**：calico 只需 3 个 tar；cilium 另需 helm 二进制 + chart .tgz。
- **要测离线但机器其实有网**也行，`is_offline=true` 就不走外网。想在已在线跑起来的集群上验证离线，**必须先 `k8s-reset` 重置再整链离线**，不能直接叠加。

按「现象 → 原因 → 解法」速查。多数已在代码里修好，这里备查。

### 部署/环境
| 现象 | 原因 | 解法 |
|---|---|---|
| `init.sh: $'\r': 未找到命令` / 语法错误 | 脚本被 checkout 成 CRLF(Windows/autocrlf) | `sed -i 's/\r$//' init.sh`;仓库已加 `.gitattributes eol=lf`,新 clone 无此问题 |
| `git pull` 报 env.yaml 冲突 | env.yaml 曾被跟踪 | 已改为 init.sh 生成 + gitignore;`git stash && git pull && git stash pop` 一次即可 |
| kubeadm 二进制 404(如 v1.34.10) | 版本号不存在 | 用真实版本(`curl https://dl.k8s.io/release/stable-1.34.txt` 查);换 minor 记得在 `k8s_compat` 加行 |
| `A template was resolved to an Omit scalar` (加 master / 拿 join / etcd 等 **delegate_to** 任务) | `connection.yaml` 曾用 `default(omit)` 给 `ansible_ssh_pass`。omit 只在"直接传模块参数"时有效,这两个是**连接变量**;root 免密时它返回 omit 哨兵,ansible-core **2.19+** 的模板引擎直接报错(老版本静默容忍)。**配好免密才触发** | 已改为 `default('')`(空密码语义等价)。老代码临时绕开:`-e ansible_ssh_pass= -e ansible_become_pass=` |
| `Failed to update apt cache after 5 retries`(同批机器有的过有的挂) | `init` 里装包(`update_cache: yes`,无 `ignore_errors`)原先排在配 DNS **之后** —— 装机 DNS 坏的机器走不到配 DNS 就中断 | 已把 DNS block 挪到软件源/装包之前。仍失败就先单跑 `--tags dns` 再跑全套 |
| 离线跑完 `/etc/apt/sources.list.d/ubuntu.sources` 内容没了 | 24.04 分支原先是 `echo "" >` 直接清空,原内容不可恢复(定制过的内网 mirror 就丢了) | 已改为 `mv` 成 `ubuntu.sources.disabled-<时间戳>`;恢复直接改回名字。22.04 的 `sources.list` 也加了 `backup: yes` |
| 离线环境 chrony 一直不同步,`chronyc sources` 全 `^?` | `chrony_ip` 写的是**域名**(如 `ntp1.aliyun.com`),而离线出不去网且 `init_config_dns: false` 不接管 DNS → 解析不了 | `chrony_ip` 改成内网 NTP 的 **IP**;或开 `init_config_dns` 并配内网 DNS |
| `env.yaml` 改了某个值但不生效,也不报错 | YAML **重复 key 静默取最后一个**。同一 key 在文件里出现两次(如在 calico 段加了 `pod_subnet`、下方"网络"段那行还在),上面那个被无声覆盖 | `grep -nE '^\s*(pod_subnet\|service_subnet):' env.yaml` 各应只 1 行;网段/VIP 相关已在 example 里归拢到一处 |
| `expected <block end>, but found '<scalar>'`(ansible 报 `Values starting with a quote must end with the same quote`) | 按块取消注释时把**说明文字**那几行的 `#` 也删了 → 变成裸标量。ansible 那句提示语容易误导成 inventory 的 `parse_kv` 问题,实际是 **env.yaml 的 YAML 语法错** | 取消注释只删每行开头那一个 `#`;改完必跑 `python3 -c "import yaml;yaml.safe_load(open('inventory/group_vars/all/env.yaml'))"` |
