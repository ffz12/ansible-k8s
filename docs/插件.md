# 集群插件

集群装好之后再装的组件，每类一个 role 加一个入口 playbook。目前实现了 device plugin、monitor、harbor-k8s。

## 约定

新增插件照这几条来，不用每次重新设计：

1. **同一类功能放一个 role，用 task 文件区分实现**。device plugin 就是一类：nvidia、rdma、以后的 dcu / npu 都是向 kubelet 上报扩展资源，所以都在 `roles/device-plugin/` 里，一个实现一个 `tasks/<名字>.yaml` + `templates/<名字>.yaml.j2`，`tasks/main.yaml` 只负责按变量 include。参照 `roles/cni`（calico / flannel / cilium 也是这么分的）。
2. **不是同一类的别往里塞**，各自一个 role 加入口 playbook，参照 `roles/nodelocaldns`。比如 dcgm-exporter 是导出 GPU 指标给 Prometheus 抓的，不上报资源，不装也不影响调度，所以不属于 device plugin。
3. **装哪些由 inventory 推导**，不手填。device plugin 读机器行上的 `accelerator_type`；不属于加速卡的能力（如 RDMA 网卡）单独给开关。
4. **离线 tar 放 `offline/artifacts/<role 名>/images/`，不进 git**，由 `scripts/offline/download-<role 名>-offline.sh` 生成，换机器 rsync 拷。
5. **镜像地址用 `{{ registry }}`**，不写死 Harbor 域名和项目名。推送复用 `docker load` 解析源名再 retag 的写法（tar 可能是 docker save 也可能是 containerd save，镜像名不一定是上游原名）。
6. **nodeSelector 用现成的节点标签**（`nvidia=true` 这类，由 `k8s-node-labels.yaml` 按 `accelerator_type` 打），不另造标签。
7. **manifest 落盘到 `/etc/kubernetes/`，apply 后等 DaemonSet ready**，并把实际 Pod 数与资源上报情况打出来 —— 没有匹配节点时 DaemonSet 期望副本是 0，`rollout status` 也会"成功"。
8. **用 helm 装的组件**：离线时 chart 的 tgz 放 `offline/artifacts/<role 名>/`（不进 git），镜像能复用已有物料就复用、不重复下载，在线时 `helm repo add` 拉官方仓库。安装用 `helm upgrade --install`，重跑就是升级，不会重复装。values 渲染到暂存目录，只写和 chart 默认值不同的项。参照 `roles/harbor-k8s`。

## device plugin

向 kubelet 上报扩展资源，Pod 才能在 `resources` 里申请。不装的话 GPU / RDMA 任务调度不上去。

```bash
ansible-playbook playbook/device-plugin.yaml                          # 按 accelerator_type 自动判断
                                                                      # 在线/离线由 env.yaml 的 is_offline 决定
ansible-playbook playbook/device-plugin.yaml -e device_plugins=nvidia  # 只装指定的
ansible-playbook playbook/device-plugin.yaml --check --diff            # 预览渲染结果, 不 apply
```

| 实现 | 上报的资源 | 装的条件 |
|---|---|---|
| nvidia | `nvidia.com/gpu` | 有 `accelerator_type=nvidia` 的节点时自动装 |
| rdma | `rdma/hca_shared_devices` | 默认装（`device_plugin_rdma: true`）。只落到带 `rdma=true` 标签的节点，该标签由 inventory 机器行的 `has_rdma=true` 打 —— 没写的机器不会跑这个 Pod。整个集群都没有 RDMA 网卡时在 env.yaml 设 `device_plugin_rdma: false` |

### 常用变量

全部变量见 `roles/device-plugin/defaults/main.yaml`，要改的写进 env.yaml。

| 变量 | 默认 | 说明 |
|---|---|---|
| `device_plugin_rdma` | `true` | 是否装 rdma 插件。没有 Mellanox 网卡的站点置 false |
| `nvidia_device_plugin_version` | `v0.17.1` | |
| `rdma_device_ids` | `["101b", "a2dc"]` | **各站点网卡型号不同，必须核对**，见下面 |
| `rdma_device_plugin_node_label` | `rdma` | 选节点用的标签，由机器行 `has_rdma=true` 打 |
| `rdma_hca_max` | `1000` | 一块 HCA 最多给多少个 Pod 用（shared 模式，不是独占） |
| `rdma_resource_name` | `hca_shared_devices` | 上报的资源名，Pod 里写 `rdma/hca_shared_devices` |

`rdma_device_ids` 填错的症状是：DaemonSet 正常起来，但节点上 `rdma/hca_shared_devices` 容量是 0 或者查不到。在 GPU 节点上查实际型号：

```bash
lspci -nn | grep -i mellanox        # 取 [15b3:xxxx] 里的 xxxx
```

一份 ConfigMap 由整个 DaemonSet 共用，插件在每台节点上拿 `vendors` + `deviceIDs` 去匹配本机实际存在的网卡：列表里有、本机没有的型号直接忽略。**所以混插不同型号时，把集群里在用的型号都列进去即可**，不用按节点分别配置。

常见型号（以 `lspci -nn` 实际输出为准）：`1017` CX-5、`101b` CX-6、`101d` CX-6 Dx、`1021` CX-7、`a2dc` BlueField-3。

### 离线镜像

```bash
# 联网机上拉, 默认双架构, 存进 offline/artifacts/device-plugin/images/<架构>/(不进 git)
bash scripts/offline/download-device-plugin-offline.sh
ARCH=amd64 bash scripts/offline/download-device-plugin-offline.sh   # 只要单架构
# 换机器: rsync -a offline/ root@控制机:~/ansible-k8s/offline/
```

两个上游镜像都是 amd64 + arm64 双架构。tar 按架构放子目录、文件名固定：

```
offline/artifacts/device-plugin/images/
├── amd64/{k8s-device-plugin.tar.gz, k8s-rdma-shared-dev-plugin.tar.gz}
└── arm64/{...}
```

role 自己探测有哪些架构（单架构站点只下一个也能跑），推 Harbor 时建 multi-arch manifest，kubelet 按节点架构自动取对应那层。手工放 tar 也行，放进对应架构的子目录即可。

**nvidia 按架构各渲一个 DaemonSet**：`libnvidia-ml.so.1` 的宿主机路径各架构不同（x86 在 `/lib/x86_64-linux-gnu/`，arm64 在 `/lib/aarch64-linux-gnu/`），而一个 DaemonSet 的 hostPath 没法按节点变，所以用 `kubernetes.io/arch` 的 nodeAffinity 分开。单架构集群只渲一个，名字不带后缀，和之前一致。rdma 不受影响（不挂宿主机库，一个 DaemonSet 覆盖所有架构）。

在线模式没有离线物料可探测，按 `device_plugin_online_archs`（默认 `[amd64]`）渲染，arm64 集群在 env.yaml 改成 `[amd64, arm64]` 或 `[arm64]`。

### 验收

```bash
# GPU 资源上报(装了插件的节点应有非空的 nvidia.com/gpu)
kubectl get nodes -l nvidia=true -o custom-columns='NODE:.metadata.name,GPU:.status.capacity.nvidia\.com/gpu'
# RDMA 资源上报
kubectl get nodes -l rdma=true -o custom-columns='NODE:.metadata.name,RDMA:.status.capacity.rdma/hca_shared_devices'
# Pod 是否都起来了
kubectl -n kube-system get ds nvidia-device-plugin-daemonset rdma-shared-dp-ds -o wide
```

跑完 playbook 会自动把上面前两项打出来。资源是 0 或空的话按这个顺序查：

1. 节点有没有对应标签（`kubectl get nodes -L nvidia -L rdma`）。没有就是 inventory 里漏写 `accelerator_type=nvidia` 或 `has_rdma=true`，补上后跑 `playbook/k8s-node-labels.yaml`。
2. 节点上 `nvidia-smi` 正常吗。驱动没装好的话插件起来也报不出资源。
3. 看插件 Pod 日志：`kubectl -n kube-system logs ds/nvidia-device-plugin-daemonset`。
4. rdma 还要核对 `rdma_device_ids` 与 `lspci -nn` 的结果。

## monitor

导出指标给 Prometheus 抓，不装不影响集群运行。目前只有 dcgm-exporter。

```bash
ansible-playbook playbook/monitor.yaml                 # 装 monitor_default_list(默认只有 dcgm-exporter)
ansible-playbook playbook/monitor.yaml --check --diff   # 预览
```

### dcgm-exporter

在 N 卡节点上导出 `DCGM_FI_DEV_*` 指标（GPU 利用率、显存、温度、功耗、时钟、NVLink）。用 `nvidia=true` 选节点，不用通用的 `gpu=true` —— dcgm 是 NVIDIA 专用，dcu / npu 节点跑它没意义。

| 变量 | 默认 | 说明 |
|---|---|---|
| `dcgm_exporter_version` | `4.6.1-4.8.4-ubuntu22.04` | tag 格式是 `<DCGM库版本>-<exporter版本>-<系统>`。**第一段必须认得节点的 GPU 驱动**，见下面「profiling 指标全空」 |
| `dcgm_exporter_custom_counters` | `true` | 用自己的 `counters.csv`（ConfigMap 挂进去）替换镜像内置的。关掉用镜像自带的 |
| `dcgm_exporter_extra_counters` | `[]` | 往白名单末尾追加整行，如 `"DCGM_FI_DEV_XXX, gauge, 说明"` |
| `monitor_scrape_mode` | `auto` | `auto` 探测有没有 ServiceMonitor CRD；也可写死 `servicemonitor` / `annotation` |
| `monitor_servicemonitor_labels` | `{}` | operator 的 `serviceMonitorSelector` 有标签要求时补上（kube-prometheus-stack 默认选 `release=<helm release 名>`） |
| `monitor_scrape_interval` | `30s` | |

**抓取方式**是这里唯一容易踩的地方。dcgm-exporter 只暴露 `:9400/metrics`，要靠 Prometheus 来抓，而怎么被发现取决于 Prometheus 的形态：

| 集群情况 | 生成什么 | 要注意 |
|---|---|---|
| 有 `servicemonitors.monitoring.coreos.com` CRD（prometheus-operator） | DaemonSet + Service + ServiceMonitor | operator 的 `serviceMonitorSelector` 若有标签要求，没配 `monitor_servicemonitor_labels` 就不会被选中 |
| 没有该 CRD（裸 Prometheus） | DaemonSet + Service + Pod 注解 | 要求 Prometheus 的 `scrape_configs` 开了 kubernetes_sd 的 pod 发现 |

判错或没配对的症状是**静默**的：Pod 正常跑、`curl :9400/metrics` 有数据，但 Prometheus 里查不到指标、Grafana 图全空。playbook 会把探测到的方式和对应的确认命令打出来。

#### profiling 指标全空（镜像的 DCGM 库版本与驱动不兼容）

症状：`DCGM_FI_DEV_*` 都正常，但 `DCGM_FI_PROF_*`（GPU 利用率、SM 占用、Tensor Core、NVLink 速率）一个都没有 —— `curl :9400/metrics | grep PROF` 空。

根因是镜像内嵌的 DCGM 库版本不认当前驱动的 DCP profiling 接口。**这个坑很隐蔽**：启动日志会打 `queried profiling metric groups count=N`，看着像支持，那只是枚举能力，运行时采不到。

H100 现网实测（驱动 `590.48.01`）：DCGM 库 `4.5.2` 全空，换到 `4.6.1` 才出数。改 `dcgm_exporter_version` 的第一段即可，滚动重启 exporter 是秒级断档，不碰驱动、不打断 GPU 任务。

两条注意：
- 只往**新**版本换。`dcgm:v1.1.1` 是 DCGM 3.3.9，比 4.5.2 还老，对新驱动更不兼容。
- 先在一个节点上试（`--limit`），确认 PROF 出数且原有 DEV 指标没掉，再推全集群。

#### SM 利用率 / NVLink 速率空（字段没启用，不是采不到）

镜像内置的 `default-counters.csv` 里 `DCGM_FI_PROF_SM_ACTIVE` 那行是**注释掉的**，`NVLINK_TX_BYTES` / `RX_BYTES` 两行**根本没有**。所以即使镜像版本对了，这三项仍然空。

`dcgm_exporter_custom_counters: true`（默认）就是为这个 —— role 把 `templates/dcgm-counters.csv.j2` 渲染成 ConfigMap 挂进容器，用 `DCGM_EXPORTER_COLLECTORS` 指过去，这三项是启用状态。

> `DCGM_EXPORTER_COLLECTORS` 是**整文件替换**不是增量追加，少写一行就少一个指标。所以模板里保留了镜像默认的全部字段（49 项）。要补字段用 `dcgm_exporter_extra_counters`，要大改就把模板拷成站点版。

distroless 镜像里没有 `cat` / `grep`，想看镜像自带的 csv 得 `docker create` + `docker cp` 抽出来。

#### 现网已有 Prometheus 的话，抓取 job 要自己核

上面两节讲的是 exporter 侧。**如果 Prometheus 不是 ansible-k8s 装的**（比如 aicloud 自带的那套在 `volcano-monitoring`），它的抓取 job 是独立配置的，role 管不着，有两个常见错法：

1. **`static_configs` 指 Service DNS**（如 `dcgm-exporter.kube-system.svc:9400`）。dcgm-exporter 的 Service 是 headless，每次抓取只命中一个 Pod，结果只有一台机器出数据，而且 `node` 标签取的是 Pod 名不是节点名。正解是 `kubernetes_sd_configs` + `role: endpoints` 逐 Pod 抓。

2. **`Hostname` 标签没覆盖**。aicloud 后端按 `Hostname=<真实节点名>` 查（如 `DCGM_FI_DEV_FB_USED{Hostname="gpu39"}`），而 exporter 自带的 `Hostname` 值是 Pod 名，筛选命中 0 条，表现为显存 / 功耗 / 温度全空。要在 `relabel_configs` 里用节点名覆盖 `node` / `nodename` / `Hostname` 三个标签。

   ⚠ 不能开 `honor_labels: true`，否则 exporter 自带的 `Hostname` 会盖过 relabel 的结果。

参考配置：

```yaml
  - job_name: 'dcgm-gpu-exporter'
    metrics_path: '/metrics'
    scrape_interval: 15s
    kubernetes_sd_configs:
      - role: endpoints
    relabel_configs:
      - source_labels: [__meta_kubernetes_service_name]
        regex: dcgm-exporter
        action: keep
      - source_labels: [__meta_kubernetes_pod_node_name]
        target_label: node
        action: replace
      - source_labels: [__meta_kubernetes_pod_node_name]
        target_label: nodename
        action: replace
      - source_labels: [__meta_kubernetes_pod_node_name]
        target_label: Hostname      # 后端按这个筛, 必须覆盖
        action: replace
```

改 configmap 后 `configmap-reload` sidecar 约 60–90 秒热加载，不用重启 Prometheus、不丢历史数据。验证：`count(DCGM_FI_DEV_GPU_UTIL) by (node)` 应返回全部 GPU 节点、每节点 8 卡。

> 手工 `kubectl patch ds` 时记得带 `--type strategic`（按 name 合并数组）。默认的 `--type merge` 会整体替换 `containers` 数组，把 image 和原有 volumeMounts 一起丢掉。
> **ansible-k8s 不吃这个坑** —— role 是渲染完整 manifest 再 `kubectl apply -f`，声明式覆盖，没有数组替换问题。

### 离线镜像与 dashboard

```bash
bash scripts/offline/download-monitor-offline.sh      # 默认双架构, ARCH=amd64 只拉一个
```

存进 `offline/artifacts/monitor/images/<架构>/dcgm-exporter.tar.gz`（不进 git）。上游镜像是 amd64 + arm64 双架构。

配套 dashboard 在 `playbook/roles/monitor/files/dashboards/gpu-node.json`（标题「GPU Nodes v2」），**需手工导入** Grafana，数据源选 `prometheus`。没做成自动导入是因为各站点 Grafana 的装法和认证方式不一样。

### 验收

```bash
kubectl -n kube-system get ds dcgm-exporter -o wide
pod=$(kubectl -n kube-system get pod -l app=dcgm-exporter -o name | head -1)
# DEV 指标(基础: 显存/温度/功耗/时钟)
kubectl -n kube-system exec $pod -- curl -s localhost:9400/metrics | grep -c '^DCGM_FI_DEV_'
# PROF 指标(profiling: GPU 利用率/SM/Tensor/NVLink) —— 为 0 就是镜像 DCGM 库版本不认驱动
kubectl -n kube-system exec $pod -- curl -s localhost:9400/metrics | grep -c '^DCGM_FI_PROF_'
# 这三项单独确认(镜像默认 csv 里没启用, 靠 dcgm_exporter_custom_counters 补上)
kubectl -n kube-system exec $pod -- curl -s localhost:9400/metrics \
  | grep -E '^DCGM_FI_PROF_(SM_ACTIVE|NVLINK_TX_BYTES|NVLINK_RX_BYTES)' | cut -d'{' -f1 | sort -u
# Prometheus 有没有抓到: 页面 Status -> Targets 里找 dcgm-exporter
```

DaemonSet 状态和 DEV 指标条数 playbook 跑完会自动打印。PROF 那几条和 Prometheus Targets 必须自己看 —— exporter 正常不代表指标齐，指标齐也不代表 Prometheus 抓到了。

### 加一种新的加速卡

以 dcu 为例：

1. 写 `roles/device-plugin/tasks/dcu.yaml`，照 `nvidia.yaml` 的结构（推镜像 → 渲染 → apply → 等 ready → 打印资源上报）。
2. 写 `roles/device-plugin/templates/dcu-device-plugin.yml.j2`，nodeSelector 用 `dcu=true`。
3. `defaults/main.yaml` 里加版本、tar 名、镜像、节点标签几个变量。
4. `tasks/main.yaml` 的 assert 里把 `dcu` 加进已支持列表。
5. 下载脚本里加一行 `pull`。

inventory 里有 `accelerator_type=dcu` 的节点时就会自动装，不用改入口 playbook。

## harbor-k8s

把 Harbor 用 helm 装进 k8s，HTTPS NodePort 对外。给业务用的镜像仓库，和装机用的 Harbor 是两套：

| | `playbook/harbor-install.yaml` | `playbook/harbor-k8s.yaml` |
|---|---|---|
| 装在哪 | 宿主机，docker-compose | k8s 里，helm |
| 什么时候装 | 装 k8s **之前**（离线装机靠它推镜像） | 集群建好**之后** |
| 证书 | 自己生成 CA 并签证书 | 用前者的 CA 另签一张域名证书 |

不能用 k8s 里的 Harbor 替代装机那个：集群起不来就没有 Harbor，没有 Harbor 离线装机又起不来集群。

```bash
ansible-playbook playbook/harbor-k8s.yaml
```

### 必填变量

| 变量 | 说明 |
|---|---|
| `harbor_k8s_domain` | 访问域名，如 `harbor.k8s.com`。**必须是域名不能是 IP** —— 证书 SAN、`externalURL`、客户端取 token 的地址都按它 |
| `harbor_k8s_storage_class` | 集群里已有的 StorageClass。**本 role 不装存储**，CSI 由站点自己准备；数据库、redis、registry、jobservice 日志都用它 |

### 常用变量

| 变量 | 默认 | 说明 |
|---|---|---|
| `harbor_k8s_https_nodeport` / `harbor_k8s_http_nodeport` | `30003` / `30002` | http 会跳转到 https |
| `harbor_k8s_node_selector` | `{}` | 各组件的 nodeSelector，如 `{ gpu: "true" }`，值必须是字符串 |
| `harbor_k8s_tls_cert_source` | `auto` | `auto` 在 `[harbor]` 第一台用装机 Harbor 的 CA 签；`secret` 用自备的 secret（含 `tls.crt` / `tls.key` / `ca.crt`） |
| `harbor_k8s_chart_version` / `harbor_k8s_image_tag` | `1.15.2` / `v2.11.2` | 两个要配套，`helm search repo harbor/harbor --versions` 看对应关系 |
| `harbor_k8s_admin_password` | 取 `harbor_admin_password` | **只在首次安装时生效**，装好后改这里不会改数据库里的密码 |

### 证书为什么复用装机 Harbor 的 CA

节点跑 `harbor-trust.yaml` 时已经信任过这个 CA。k8s 里的 Harbor 用它签的证书，节点不用配 `insecure-registries`，containerd 的 `hosts.toml` 现有模板（https）直接能用。走 HTTP 的话每台节点都要单独配，`ctr` 要加 `--plain-http`，`skopeo` 要加 `--tls-verify=false`。

证书 SAN 只放域名，端口不进 SAN，换 NodePort 不用重签。签名在 CA 那台做，`ca.key` 不分发。SAN 配置没变就不重签，重跑不会换证书。

### 离线物料

**镜像不用另外下载**，复用装机 Harbor 的。装机 Harbor 的离线包就是同一批 goharbor 官方镜像，版本也是 `v2.11.2`，而且那台已经 `docker load` 过，本地就有 `goharbor/<名>:v2.11.2`。playbook 在那台上 `docker tag` 后推进它自己的仓库（`{{ registry }}`），k8s 里的 Harbor 从那里拉。已经在仓库里的跳过。

所以 `harbor_k8s_image_tag` 要和装机 Harbor 的版本一致。本地缺镜像时会报出缺哪几个，`docker images | grep goharbor` 看实际有哪些。

**只需要准备 chart**，在联网机上：

```bash
helm repo add harbor https://helm.goharbor.io
helm pull harbor/harbor --version 1.15.2 -d offline/artifacts/harbor-k8s/
```

得到 `offline/artifacts/harbor-k8s/harbor-1.15.2.tgz`（不进 git），rsync 到控制机。trivy 默认关闭，不需要它的镜像。

### 装完让节点能拉这个仓库

`env.yaml` 的 `harbor_instances` **末尾**追加一项（`harbor_dns` / `registry` 取的是第一项，不能插在前面）：

```yaml
harbor_instances:
  - { dns: "harbor.local.clusters", ip: "172.171.0.206" }
  - { dns: "harbor.k8s.com:30003",  ip: "172.171.0.201" }   # ip 填任一节点
```

再跑 `playbook/containerd-setup.yaml`，它会写 `hosts.toml` 和 `/etc/hosts`。`dns` 带端口没问题：`/etc/hosts` 写入时会去掉端口，`certs.d` 目录名和 docker 那边保留 `host:port`。

**CA 信任不用另外配。** `harbor-trust.yaml` 只处理 `harbor_instances` 第一项：把 CA 装进系统信任库，再写 `/etc/docker/certs.d/<第一项域名>/ca.crt`。新域名在 `certs.d` 下没有目录，docker 会退回用系统信任库；证书又是同一个 CA 签的，所以直接被信任。containerd 同样认系统信任库。

前提是 k8s 里的 Harbor 用 `harbor_k8s_tls_cert_source: auto`，即同一个 CA。改成 `secret` 并用别的 CA 签证书时，要自己把那个 CA 装到各节点。

### 要注意

- **共享存储掉挂会静默写进本地盘**。StorageClass 是 hostPath 类（如 local-path 指向共享目录）时，共享文件系统掉挂后 hostPath 访问到的是节点本地目录，不报错。CSI 类存储没有这个问题。
- **数据库跑在共享存储上**，存储要满足 Postgres 对文件锁和持久化的要求。Harbor 数据库是单实例，不是高可用。
- **PVC 的容量不一定是硬配额**，取决于 CSI 实现。
- **备份要单独做**。StorageClass 的 `Retain` 只是删 PVC 时不删数据，不是备份。
